## 4. Submission ステータス遷移

```
           [依頼作成]
               ↓
           pending
               │
          [編集開始・自動]
               ↓
          in_progress ◄───────────────────────────────────┐
               │ \                                         │
          [提出]  \[強制提出で巻き込まれた場合]       [再提出]
            ↙   ↘   ↘                                     │
  [整合エラー] [OK] cancelled                              │
  （ブロック）   ↓                                         │
            submitted ──────────────────────────────────→ │
               │ \      [親が差し戻し → revision_requested]│
     [親がマージ] \                                        │
               ↓  ↘[コンフリクト → conflict_fields 記録]  │
            merged                                        │
```

**ステータス一覧**（`docs/14-delegation-model.md` §3 参照）:

| ステータス | 説明 | 誰が遷移させるか |
|---|---|---|
| `pending` | 依頼作成済み・未着手 | 自動（依頼作成時） |
| `in_progress` | 編集中 | 自動（最初の PUT 時） |
| `submitted` | 提出済み。親のマージ待ち | 担当者が「提出」ボタン |
| `merged` | 親がマージ済み | 親 coordinator が「マージ」 |
| `revision_requested` | 差し戻し中 | 親 coordinator が「差し戻し」 |
| `cancelled` | 強制取消 | 親が「強制提出」を実行 |

**削除したステータス**: `accepted`（不要と判断）

- 提出（`submitted`）はマージ待ち状態。自動マージは行わない（Q-B 改訂）
- 親 coordinator が明示的に「マージする」を押したとき初めて 3-way merge が実行され、親の submission_rows に反映
- 親が「現状を確認・反映」を押せば、子が未提出のままでも途中状態を親のワークスペースに取り込める（子 status は変わらない）
- 配下が全員 `merged` または `cancelled` になれば親は自分の Submission を提出できる
- 最上位 coordinator が submit したとき allocation_rows に反映される
- 強制提出時: 配下の未完了 Submission がすべて `cancelled` に遷移し、partial merge が親のワークスペースに反映

## 6. Phase B 実装前の確認事項

> ✓ = 解決済み、❓ = 確認待ち

### ✓ Q-A【解決済み】承認（submitted → accepted）は誰が、どこから実行するか

**決定**: `accepted` ステータスを廃止。提出（`submitted`）と同時に 3-way merge が自動実行され、coordinator の編集画面に即座に反映される。coordinator による明示的な承認操作は不要。  
詳細: `docs/14-delegation-model.md`

---

### ✓ Q-B【改訂済み】取りまとめ担当が「マージ確認」を行うタイミングと UI の位置

**当初決定（改訂前）**: マージは自動実行（提出時）。

**改訂後決定（2026-06-07）**: マージは **親 coordinator が明示的に実行する（手動マージ）**。理由：
- 担当者の提出 = 「返しました」の意思表示であり、内容確認は親の責任
- コンフリクト確認・差し戻し判断を親が行う必要があるため自動化は不適切

**操作の種類**:
- `POST /submissions/:id/merge`: 配下が `submitted` → 親が明示的にマージ（子 status → `merged`）
- `POST /submissions/:id/sync`: 配下が `in_progress`/`pending` → 親が途中状態を取り込む（子 status 変わらず）

S-04（DiffReviewView）は Phase C で実装するオプション差分確認画面として位置づけは変わらないが、マージ自体は PortalView の「マージする」ボタンから実行する。

---

### Q-C 委任を追加できるのは SubmissionEditView 内か、PortalView からか

**背景:** coordinator が子委任を追加する UI がない（現状は adminのRoundDetailViewからのみ）。  
§8-2 に「取りまとめ担当は Submission の範囲をさらに細かく担当者へ委任できる」とある。

**選択肢:**
- Submission 編集画面（S-03）のフッターに「委任を追加」ボタン
- 依頼一覧（PortalView）の各 Submission 行に「委任を追加」ボタン
- 両方に配置

---

### ✓ Q-D【解決済み】差し戻し時、孫 Submission のステータスはどうなるか

**決定**: 差し戻しは 1段のみ。孫 Submission は連動しない（差し戻し対象の child のみ `revision_requested`）。  
理由: 連鎖差し戻しは実装・運用ともに複雑になりすぎる。child が孫をどう扱うかは child（coordinator）の判断に委ねる。

---

### ✓ Q-E【解決済み】担当者（member）がさらに依頼できるか

**決定**: 依頼（旧：委任）できるのは **coordinator 以上のみ**。member には依頼機能を付けない。依頼が必要な場合は coordinator ロールに変更する。
- coordinator → coordinator への依頼は可能（実装済み）
- member → 誰への依頼も不可（サーバーで 403 を返す）
- admin → coordinator または member への依頼は可能

用語整理: 「委任・委譲」は適切でなく、主担当が必要な情報を入力して返してもらう「依頼」の概念が正しい。UI・ドキュメントは「依頼」で統一する（変数名・DB カラム名は変えない）。

---

### ✓ Q-F【解決済み】「提出」ボタンの前提条件（配下あり coordinator の場合）

**決定**: 強制提出オプションを実装する。
- 通常提出: 配下の Submission がすべて `submitted` または `cancelled` のときのみ可能
- 強制提出: 配下に未提出がある状態でも提出可能。未提出の配下（直接・孫以下すべて）は再帰的に `cancelled` に遷移し、partial merge が trunk に反映される
- UI: 通常提出が 409 で返ってきたとき `window.confirm` で強制提出を促す
- `cancelled` になった Submission は member 側で「取消済み」バッジで表示（編集不可）

---

### ✓ Q-G【解決済み】PortalView の依頼一覧に「配下の進捗」を表示するか

**決定**: 表示する。
- `GET /api/submissions` に `child_count` / `child_done_count` を追加（サブクエリ）
- PortalView の一覧に「配下 N/M 完了」列を追加（child_count=0 のときは「—」）
- `submitted` と `cancelled` 両方を「完了」にカウント
