# 09 — サーバー移行ビジョン

> **ステータス**: 企画段階（2026-06）  
> 設計・実装の詳細はこのドキュメントが承認されてから別ドキュメントに分離する。

---

## 1. 現状の課題

### 1-1. 分割ファイル運用の限界

現在の運用では、グループ会社全体の発令データを**部門ごとに Excel ファイルを分割**して各担当者に配布し、後から取りまとめ担当がマージしている。

| 課題 | 具体的な影響 |
|---|---|
| 出向・兼務の整合不能 | 同一グループ社員 ID を持つ人が「出向元ファイル」「出向先ファイル」の両方に存在し、band・ポジション番号・グループ ID の整合を**手作業で確認・依頼**しなければならない |
| 矛盾の発見が遅い | ファイルがマージされるまで整合エラーが発見できない |
| 受け渡しコスト | 別担当が作ったポジション番号・グループ ID を Slack や Excel で手渡ししている |
| 新規ポジション払い出しの属人化 | 採番ルールが暗黙知化しており、ファイルへの手書き記入で管理されている |

### 1-2. 階層別担当の複雑性

部門単位の分割に加えて、**組織階層ごとに担当が異なる**という構造がある。

- **3 階層以上（組織長層）**: 100 人以上を専任担当が管理。新組織の組織長ポジション作成も担当。
- **2 階層以下（メンバー層）**: 1,000 人以上を部門別に分割してさらに担当者が管理。3 階層直下との重複あり。

現状のツールは「全員を組織ボックスに並べる」ビューのみのため、**組織長専任担当には人が邪魔で使いにくい**という問題がある。

### 1-3. Excel 下位互換性の構造的限界

Excel を編集媒体・提出媒体・受け渡し媒体として使い続けると、以下の機能が実現できない。

- **行レベルのアクセス制御**: 現状は「ファイルを分割することで」擬似的に実現している。Assignee フィールドは本来「アクセス制御（誰が見れるか）」と「ルーティング（今誰が担当しているか）」の 2 つの役割を兼ねており、中間担当が動的に書き換えながら分割管理している。このため同一行を複数担当者が扱う重複ケースを構造的に表現できない
- **改版管理・変更通知**: ファイルの上書き保存のため誰がいつ変えたか追えない
- **担当者間の確認フロー**: コメント・承認をセル内テキストで代替しており、構造化できない

## 2. 目指す姿

### 2-1. 中央データベースを信頼源にする

```
【現状】
Excel(部門A) ──┐
Excel(部門B) ──┼── 手動マージ ── 取りまとめ担当 ── 人事システム
Excel(部門C) ──┘

【目標】
各担当者(Web) ──┐
各担当者(Web) ──┼── Aurora(中央DB) ── 自動チェック ── 取りまとめ担当 ── 人事システム
各担当者(Web) ──┘
                    ↑ Excel はインポート/エクスポートの形式として残る
```

### 2-2. 自動化できる調整は自動化する

現在「依頼→待ち→返信」で行われている担当者間のやり取りのほとんどは、**共有 DB があれば自動解決できるデータ同期問題**である。

| 現在の手作業 | DB 化後の扱い |
|---|---|
| 出向元・先の band 一致確認依頼 | 提出時の自動バリデーション（同一 groupMemberId 行間で比較） |
| グループ ID の受け渡し | 同一 userId/groupId を持つ行をシステムが自動リンク |
| ポジション番号の受け渡し | ポジションコードを中央管理。担当者は参照するだけ |
| 新規ポジション払い出し依頼 | ポジション申請ワークフロー（後述） |

整合が取れないケースのみ、関係する両担当者へ自動通知する。

### 2-3. 残る「人間が判断すること」を最小化する

システムが代替できない判断のみを担当者に問う：

- 業務上の意思決定（この人は A 組織か B 組織か）
- システムフラグに対する最終確認
- 新ポジションのグレード・役割の定義

コメント機能よりも、**システムが問題を検出して通知 → 担当者が確認・承認する軽量フロー**が実態に合う。

## 3. 解決案：ハイブリッド段階移行

### フェーズ 1 — サーバー追加（UX 最大継承）

**変えること**: 「ローカル保存」を「サーバー提出」に変えるだけ。  
**変えないこと**: Excel での編集・インポート・エクスポートの操作感。

- AWS Aurora に中央 DB を構築
- 担当者は Excel を編集し、Web からアップロードして提出
- 提出時に出向/兼務の整合チェックを自動実行
- エラーがあれば関係担当者にメール通知（通知アダプタ経由。実装は未定）
- SSO 連携によるユーザー認証を導入（認証アダプタ経由。実装は未定）
- **アクセス制御はポリシーベースで実現**（後述）。Assignee フィールドは「主担当・通知先」の意味に絞り、Excel フォーマットは変更しない
- ポジション申請ワークフローを追加
  - 担当者が「この組織に新ポジションが必要」とリクエスト
  - 管理者が positionCode を付与（または自動採番）
  - 採番完了を通知 → AllocationRow に自動反映

### フェーズ 2 — Web 編集の追加（Excel の役割縮小）

**変えること**: 担当者が Web 上で直接行を編集できるようになる。  
**変えないこと**: Excel インポート/エクスポートは引き続き可能。

- 担当者が Web 上で直接行を編集できるようになる
  → この時点で Excel は「編集媒体」としては終了し、インポート/エクスポート専用になる
- 階層別ビュー（組織長専任向け：組織ノードのみ表示、人物を非表示にできる）を追加
- ad-hoc な行の担当者付け替えを Web UI で操作可能に

### フェーズ 3 — Excel は出力専用（Web ファースト）

**変えること**: 担当者の主な作業場所が Web になる。  
**変えないこと**: HR システム連携のための Excel エクスポートは継続。

- Excel は HR システムへの出力フォーマットのみ
- 改版管理・変更通知・コメントが Web で完結
- 担当者ロール・権限の細かい制御が可能に

## 4. アクセス制御方針

### ポリシーベースアクセス制御（Phase 1 から適用）

行に Assignee リストを書く代わりに、**ユーザー側にアクセス範囲（スコープポリシー）を定義**する。

```
User A（3階層担当）  → orgLevel >= 3 の行が見える・編集できる
User B（部門A担当）  → orgCode IN ('A01','A02') の行が見える・編集できる
User C（部門A上位） → orgLevel >= 3 AND orgCode IN ('A01') の行
```

- 重複行（3 階層かつ部門 A）は A・C 両方のユーザーに自動的に見える
- Excel の `assignee` 列は「主担当・通知先」の意味に絞る。フォーマット変更なし
- ad-hoc な付け替え（中間担当が特定行だけ別の人に回す）は DB 側の override で対応し、Excel には書かない

### 出向・兼務の整合確認：最小開示の原則

出向元・出向先は別会社であり、相手方の行全体を照会できるようにすることは情報セキュリティ上のリスクになる。

**方針**: 相手方のデータは見せず、**システムが矛盾フィールドの値ペアだけを開示する**。

```
整合エラーの通知例:
  Person G001 の band が一致しません
  出向元(A社): band = 4
  出向先(B社): band = 3
  → どちらかの担当者が修正依頼を送る or 自社側を修正
```

業務判断が必要なケース（どちらの値が正しいか不明）はコメントを添付した修正依頼フローで解決する。完全な照会権限は与えない。

## 5. Excel 下位互換性の方針

### 「編集媒体」と「データ形式」を分離して考える

| 用途 | Phase 1 | Phase 2 | Phase 3 |
|---|---|---|---|
| データ編集 | Excel（従来通り） | Excel または Web | Web（主体） |
| 提出・インポート | Excel アップロード | Excel または Web | Web |
| HR 連携エクスポート | Excel 出力 | Excel 出力 | Excel 出力 |

### 既存 Excel ファイルの継続利用

Phase 1 では既存の Excel フォーマット（現行のインポート仕様）を変更しない。アクセス制御はサーバー側のポリシーで完結するため、Excel 列の追加は不要。Phase 2 以降で列が増える場合は後方互換（旧列がなくてもインポートできる）を維持する。

## 6. アーキテクチャ方針

### ドメイン層を変えずにアダプタを差し替える

現在のドメイン層（`src/domain/`）は外部依存ゼロの純粋関数群であり、そのままバックエンドに移植できる。

```
ports/
  IAllocationRepository      ← 既存ロジックが依存するインターフェース
  IUserRepository             ← 新規
  INotificationPort           ← 新規（実装はアダプタで差し替え）
  IAuthPort                   ← 新規（実装はアダプタで差し替え）
  ICommentRepository          ← 新規

infrastructure/
  local/          ← 現行の LocalStorage 実装（Phase 1 でも継続）
  aurora/         ← Phase 1 から追加
  notification/   ← 通知アダプタ（実装未定）
  auth/           ← 認証アダプタ（実装未定）
```

バリデーション・EditCommand・UndoStack はポートに依存するため、**アダプタ差し替えでドメインロジックの変更は不要**。

### Aurora テーブル概念（最小構成）

```sql
sessions                -- インポート単位（現行のセッション概念を継承）
allocation_rows         -- AllocationRow（フィールドをカラムとして保持）
user_access_policies    -- user_id × orgLevel_min × orgCodes[]  ← ポリシーベースアクセス制御
row_assignee_overrides  -- row_id × user_id  ← ad-hoc な付け替え（DB 専用、Excel に非依存）
positions               -- ポジションマスタ（払い出しワークフロー管理）
consistency_issues      -- groupMemberId × field × valueA × valueB × status  ← 整合エラー管理
comments                -- issue_id × author_id × body × created_at
notifications           -- recipient_id × template × payload × sent_at
```

## 7. 設計を詰める順番

1. **ユーザー管理・ポリシーベースアクセス制御** — 全機能の前提。認証アダプタの選定も並走
2. **出向/兼務の自動整合チェック** — Aurora 移行時の最初の一貫性バリデーション。最小開示での通知フローも含む
3. **ポジションコード管理**（新規払い出しワークフロー）— 独立性が高く並走できる
4. **通知アダプタ**（実装未定）— 2・3 の通知先として必要
5. **Web 編集 + 階層別ビュー**（Phase 2 の中心機能）
