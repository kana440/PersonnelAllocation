## 背景

自前実装のキャンバス仮想化（パネル単位・行単位）とドラッグ最適化を実装した際、「ドラッグ可能なボックス＋接続線＋ズーム/パン＋仮想化」というこの種のUIは React Flow（`@xyflow/react`）のようなノード図ライブラリが既に解決している領域だと気づき、本番キャンバス（`apps/web/src/components/canvas/`）の置き換えを検討した。

## 検証済み・確認できたこと（有効な結論）

- **MIT ライセンス**: `@xyflow/react` のコード自体は MIT。ただし右下の attribution（ウォーターマーク）を消すには公式に Pro サブスクリプション（$169/月〜）が必要（利用規約上）。消さない前提で使う分にはライセンス上の制約はない
- **性能**: 2000組織・3万行相当の合成データ・実データの両方で、初期表示・編集後の再描画とも実用的な速度で動くことを確認済み（`onlyRenderVisibleElements` による自動仮想化 + 既存の `treeWindowLayout.ts` の `computeLayout()` 流用で十分）
- **ドラッグ&ドロップ互換性**: RowCard の HTML5 ネイティブドラッグ&ドロップは、ノード要素に `className="nodrag"` を付けることで React Flow 自身のノードドラッグ（d3-drag）と共存できる。チャット・連絡票・不在パネルへのドラッグも、native DnD の `dataTransfer` JSON契約に依存しているだけなので影響を受けない
- `treeWindowLayout.ts` の `computeLayout()`（木構造の座標計算）はそのまま流用できる。React Flow 自体に自動レイアウト機能はないが、代替する必要はない

## 統合作業でつまずいた具体的な技術的落とし穴

再挑戦する場合に同じ罠を踏まないための記録。

1. **`childrenMode: 'inline'` は旧実装ではネスト描画されるだけで、独立した `PanelDef` を持たない**。React Flow ではこの区別が意味を持たないため、「開いているパネルの配下組織を丸ごと展開してノード化する」という設計に置き換える必要があった（`collectDescendantIds` で対応）。
2. **CSS: `display:flex; flex-direction:column` の親に `height` を固定しても、測定・適用のタイミング次第で効かないことがあった**。最終的には `maxHeight`（上限）だけを指定し、中身に応じて自然に縮む・伸びる設計にして、実測値は `ResizeObserver` で取得する方式に落ち着いた。
3. **`offsetHeight` と `getBoundingClientRect().height` の違い**: React Flow のズームは CSS `transform: scale()` で実装されている。`getBoundingClientRect()` は画面上の見た目のサイズ（ズーム後）を返すため、フロー座標系の値である `node.height` に渡すと拡大率でズレる。`offsetHeight`（レイアウト上のサイズ、ズームの影響を受けない）を使う必要がある。
4. **`useNodesState` は `useState` と同じで、渡した初期値は初回にしか効かない**。パネルの開閉等で入力が変わっても自動反映されないため、明示的な同期処理（新規ノードの追加・不要ノードの除去）を書く必要がある。この同期処理で「既存ノードの位置を毎回上書きする」実装をすると、実測で更新した高さと位置がズレて重なる・間延びする不具合になった（既存ノードは保持し、新規追加分だけ足す方式が正解）。
5. **`computeLayout` の `subtreeW`（本番コード）に循環参照ガードがなかった**。Phase A では「開いている組織の配下を丸ごと」という、本番の実際の運用より大きい範囲を一度に計算する使い方をしたため、循環参照ガード追加（`treeWindowLayout.ts`、本番コードとして残置）。ただしこれが根本原因かは未確認。

## 未解決のまま中断した問題

別のPC・クリーンインストール環境で「組織の箱は表示されるが、中の人物が一切表示されない」という再現不能な不具合が発生。ブラウザコンソールのエラー内容を確認できないまま、これ以上の推測ベースの修正は非効率と判断し、Phase A の本番統合を中断した。
