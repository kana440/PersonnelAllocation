# 12 — STEP2 サービス要件定義

> **ステータス**: ドラフト（2026-06）  
> **用途**: チームメンバー・企画書向けのイメージ合わせ用。ToBe の業務フロー・ルール・機能要件を記述する。  
> STEP1（Excel ローカル運用）は `docs/01-requirements.md` 参照。技術的移行計画は `docs/09-migration-vision.md` 参照。

---

## 1. 背景：STEP1 の限界と STEP2 が解決すること

STEP1 は「ブラウザ完結・サーバーなし」で動作する Excel 補助ツールとして、操作の可視化・Undo/Redo・AI 支援などの価値を提供してきた。一方で Excel をデータの受け渡し媒体にする構造上、以下の課題が本質的に解決できない。

| 課題 | 具体的な影響 |
|---|---|
| 担当者間の照合が手作業 | 出向元・出向先の band 一致をメールや Excel で手渡し確認している |
| 矛盾の発見が遅い | マージ後にしか整合エラーが見えない |
| ポジション番号の属人化 | 採番ルールが暗黙知。別担当者へのコード共有がメールや口頭で手作業 |
| 改版・変更通知がない | ファイルを上書き保存するため誰がいつ何を変えたか追えない |
| 担当者間のやり取りが非構造 | 依頼・確認がセル内テキスト・メール等に分散 |
| 組織構造変更への追随が手作業 | 4月直前まで組織が変わるたびに各担当への影響確認・通知を手動で行っている |

STEP2 は「中央 DB（Aurora）＋ Web 編集＋ SSO 認証」を導入することで、これらを構造的に解決する。

## 2. ToBe 業務フロー全体像

```
【STEP1 現状】
  管理者（HRサービス部門）
    ↓ SuccessFactors からデータ抽出 → Excel 作成 → 担当別に分割配布
  HR担当（部門ごと）・職場の部門長
    ↓ Excel 編集 → メール返送
  管理者
    ↓ 手動マージ → 整合確認（メール往復）→ 再依頼 → …
    ↓ 最終 Excel → SuccessFactors 登録

【STEP2 ToBe】
  管理者
    ↓ SF から抽出 or Excel インポートで Round（申請回）を作成・ベースデータ整備
    ↓ 取りまとめ担当ごとに担当領域を指定して委任依頼（コメント付き）
    ↓ システムが取りまとめ担当へメール通知（URL付き）

  取りまとめ担当（HR担当・部門ごと）
    ↓ SSO ログイン → 依頼一覧で自分の担当範囲と依頼コメントを確認
    ↓ 直接編集して提出 or 範囲を絞って職場の部門長等へ委任（コメント付き）
    ↓ ポジション新設・人追加も可能。作成したポジション番号は関係担当へ自動共有
    ↓ 配下全 Submission 完了後、自分もマージ確認して「提出」

  担当者（職場の部門長または委譲先メンバー）
    ↓ SSO ログイン → 委任された範囲と依頼コメントを確認
    ↓ Web 編集 or Excel エクスポート→修正→アップロード
    ↓ 「提出」（自分の Submission を完了）

  管理者
    ↓ 提出状況ダッシュボードで進捗管理・差し戻し（コメント付き）
    ↓ 並列で走っている Round があれば Cross-Round マージを実行
    ↓ Cross-Round コンフリクトがあれば関係する上位取りまとめ担当と解消
    ↓ 整合チェック（出向・兼務の自動検出）・統計的異常確認
    ↓ 最終提出 → 新 Revision（改訂版）を確定 → SF 登録
```

## 3. データモデル：Revision / Round / Submission

### 3-1. 3 つの概念

STEP2 の中核となるデータ構造は 3 層で構成される。

| 概念 | 日本語名 | 定義 | Git での類似概念 |
|---|---|---|---|
| **Revision** | 改訂版 | SuccessFactors に反映された（または反映予定の）正式確定状態。不変。次の Round の出発点。 | タグ付きコミット（main ブランチ）|
| **Round** | 申請回 | ある Revision から次の Revision を作るための作業単位。年 2 回（1月・3月）が基本。委任ツリーを構成する複数の Submission を束ねる。 | フィーチャーブランチ |
| **Submission** | 提出物 | Round 内で 1 人の担当者が担当範囲を編集して提出した変更のまとまり。委任ツリーの 1 ノード。 | コミット |

```
Revision 1（2025年3月版 確定）  ←  SF に登録済みの正式状態（不変）
    │
    ├── Round A（2026年1月版）    ← 年2回のうち1回目
    │     │
    │     │  ← 委任ツリー（下から順次 bottom-up にマージが進む）
    │     │
    │     ├── 管理者（発行者・確定者）
    │     │     ├── 田中さん（取りまとめ・人事本部）      ← マージ結果確認者①
    │     │     │     └── 山田さん（担当者・HR推進室）   ← Submission 提出
    │     │     ├── 鈴木さん（取りまとめ・技術本部）      ← マージ結果確認者②
    │     │     │     ├── 佐藤さん（担当者・技術2課）    ← Submission 提出
    │     │     │     └── 伊藤さん（担当者・技術3課）    ← Submission 提出
    │     │     └── ── …
    │     │
    │     └── 全ツリー完了 →
    │
    └── Round B（2026年1月版 局所修正）  ← 同一期内の修正 Round（同時並行）
          └── 管理者 → 担当者（HR部門）
                ↓ 完了
                ↓ Round A と Round B の Cross-Round マージ → コンフリクト検出・解消
                ↓
Revision 2（2026年1月版 確定）  ←  新しい正式状態
```

### 3-2. Revision（改訂版）の性質

- **不変（immutable）**: 一度作成されたら内容は変更できない
- **連番**: Rev.1, Rev.2, Rev.3 … と連番で管理される
- **ラベル**: 人間向けの名称（`2026年1月版 確定`、`2026年3月版 確定`）を付与できる
- **作成タイミング**: Round の委任ツリー全体が完了し、管理者が最終確定したとき
- **SF との対応**: 各 Revision は SF への登録申請の単位となる
- **ベース参照**: すべての Round は必ずいずれかの Revision をベース（`basedOn`）として参照する

**Revision ライフサイクルにおける役割分担**:

| 役割 | 担当者 | 内容 |
|---|---|---|
| **発行者** | 管理者 | Round を作成し、ベースデータを整備して委任ツリーを起動する |
| **マージ結果確認者** | 委任を出した親ノード（取りまとめ担当・各レベル） | 自分の直接の委任先（子 Submission）が全員提出したら、合算結果を確認する。委任ツリーの各ノードが bottom-up に担う役割。取りまとめ担当が複数段いれば、各段でそれぞれ確認が発生する。 |
| **修正者** | マージ結果を確認した親ノード（優先）／差し戻し先の子ノード | 問題を発見した親が自分のスコープで解決できれば自分で直す。解決できない場合は該当の子 Submission を差し戻して再提出を依頼する（コメント付き）。 |
| **コンフリクト解消者** | 競合した Submission の直近の共通上位取りまとめ担当 | 同じ行を変更した複数の Submission が合流するノードで解消を担う。ツリーの最上位（管理者直下）同士の競合のみ管理者が解消する。 |
| **確定者** | 管理者 | 委任ツリーの全 Submission が集約・マージされた最終状態を確認し、Revision を確定する。 |

> **重要**: 確定者（管理者）は、異なるブランチから上がってきた修正がすべて合流するポイント。どの子ブランチの修正も親を経由して順次積み上がっていくため、管理者が確定できるのは「全ツリーが完了した瞬間」であり、時系列（カレンダー上の日付）では決まらない。これが Revision の切れ目が時系列で綺麗にならない根本的な理由。

### 3-3. Round（申請回）の性質

| 属性 | 説明 |
|---|---|
| `basedOn` | どの Revision をベースにするか（必須）|
| `kind` | `'annual'`（年次正式申請）or `'patch'`（局所修正）|
| `scope` | Round の対象範囲（全社 / 特定組織 / 特定条件）|
| ライフサイクル | `draft` → `in_progress` → `ready` → `merged` → Revision 確定 |

**基本サイクル**:

年 2 回が基本サイクル（1月版・3月版）。それ以外に局所修正（`patch`）が発生することがある。ただし「Round の外にある変更」は存在しない——すべての変更は必ずいずれかの Round を経由して次の Revision に反映される。

| | `annual`（年次） | `patch`（局所修正） |
|---|---|---|
| 発生頻度 | 年 2 回（1月・3月）確定 | 必要に応じて随時 |
| 対象範囲 | 全社 | 特定組織・少数行 |
| 委任ツリー | 深い（多段委任・全グループ）| 浅い（1〜2段）|
| 承認プロセス | フルワークフロー | 簡略化 |

**同一期に複数 Round が走ることがある**:

1月版の `annual` Round が進行中に、別件の `patch` Round が同じ Revision をベースに発行されることがある。この場合、両 Round が完了した段階で Cross-Round マージ（§3-5b）を経て次の Revision が生成される。

### 3-4. Submission（提出物）の性質

- **委任ツリーの 1 ノード**に対応する。担当者 1 人 × 担当範囲 × Round の組み合わせ
- ステータス: `pending` → `in_progress` → `submitted` → `accepted`（または `revision_requested` で差し戻し）
- 委任先の Submission がすべて `accepted` にならないと、委任元は `submitted` にできない
- **Submission の変更内容 = Row の差分リスト**（どの行をどう変えたかの記録）

### 3-5a. ツリー内 bottom-up マージ（単一 Round 内）

1 つの Round でも、委任ツリー全体が完了するまで時系列は綺麗に切れない。

**なぜ時系列で切れないか**:

- 委任ツリーの異なるブランチ（例: 人事本部系と技術本部系）は**独立して並行**して進む
- あるブランチが完了しても、別ブランチはまだ編集中という状態が当然起きる
- 各親ノードは「自分の直接の子が全員揃ってから」マージ確認を開始する → 親が確認できるタイミングもブランチによって異なる
- 修正が発生すると、子→親→その親 と順次影響が伝播する（差し戻し・再提出の連鎖）

**bottom-up マージの流れ**:

```
担当者 A（技術2課）    担当者 B（技術3課）
    ↓提出                  ↓提出（後で）
    ↓                      ↓
鈴木さん（技術本部・取りまとめ）← 両者が揃ってから「マージ結果確認」
  ├ A と B の差分を統合 → 技術本部単位の合算 Submission
  ├ 競合あり（A と B が同じ行を変更）→ 鈴木さん（共通上位）がコンフリクト解消
  ├ 問題あり → 自分で解消できる場合: 直接修正
  └ 問題あり → 自分では解消できない場合: 担当者 A or B に差し戻し（再提出依頼）
         ↓ 解消後、再提出
         ↓
管理者（← すべての取りまとめ担当の合算が揃ってから最終確認）
  ├ 技術本部系 + 人事本部系 + 営業本部系 … を統合
  ├ 直下の取りまとめ担当同士の競合のみ管理者が解消（それ以下は各取りまとめ担当が解消済み）
  ├ 問題あり → 取りまとめ担当に差し戻し（コメント付き）
  └ 全グループ確定 → Revision 生成
```

**修正の連鎖**:
ある担当者の修正が確定すると、その差分は親・親の親と順次積み上がっていく。全グループ会社に影響するデータ（band・組織コード等）は最終的に管理者が確認する最上位でのみ全体整合が保証される。

### 3-5b. Cross-Round マージ（複数 Round 間）

複数の Round が同じ Revision をベースに**同時並行**で走ることがある。

```
Revision 2 をベースに:
  Round C（2026年3月版 年次）  ─── 全社規模で進行中
  Round D（技術部 緊急異動）    ─── 同時に走っている

両 Round が完了 →
  非重複行（片方だけが変更した行）: 自動マージ ✅
  重複行（両方が同じ rowId を変更）: コンフリクト 🔴 → 管理者が解消
  解消後 → Revision 3 確定
```

**コンフリクト解消 UI のイメージ**:

```
コンフリクト: rowId 1042（山田 太郎 / 人事本部）

  Round C（3月版）の変更:   departmentCode: HR01 → HR02
  Round D（緊急異動）の変更: departmentCode: HR01 → TEC01

  [Round C の変更を採用]  [Round D の変更を採用]  [手動で値を入力]
```

> Cross-Round のコンフリクト解消は、競合する変更を持つ Submission の **共通上位取りまとめ担当**が担う。ツリーの最上位（管理者直下）同士の競合のみ管理者が最終判断する。解消材料（どちらの変更が業務的に正しいか）は各 Round の背景を持つ担当者が最も熟知しているため、管理者による一方的な上書きではなく関係者の合意を経ることを推奨する。

### 3-6. Round ベースデータの整備（Revision からの引き継ぎ）

新しい Round を作成するとき、直前の Revision のデータをそのまま「before（Prev）値」として使えない場合がある。Revision が確定してから次の Round が始まるまでの間に、実際の人員・組織が変化しているためである。

**なぜ必要か（現状の Excel 運用との対比）**:

| 現状 | ToBe |
|---|---|
| 1月 Revision（ファイル）を手元に置いて、3月用を一から手作業で再作成 | 1月 Revision + 期間中の変化差分 = 3月 Round のベースデータをシステムが生成 |
| 入退社・異動の反映漏れが起きやすい | 変化リストを確認・適用する工程が構造化される |
| 前回からの変化点が一目でわからない | 1月 Revision からの差分として担当者が確認できる |

**1月 → 3月 Round 間に起きる変化（主なもの）**:

| 変化の種類 | データへの影響 | 対応 |
|---|---|---|
| 入社 | 新しい行を追加（after 欄は空） | 取りまとめ担当がポジション・配属を記入 |
| 退社 | 対象行を削除マーク（移動区分=削除 相当） | 担当者が確認して確定 |
| 異動・転籍（Prev が変わる） | `departmentCode` 等の Prev 値を更新 | 変化行に「Prev 更新あり」フラグ |
| 出向・出向受入の開始/終了 | 対象行の `concurrentType` 等を更新 | 出向元・出向先の担当者双方に通知 |

**システムが行う処理（ベース整備ステップ）**:

```
管理者が「次の Round を作成」操作
  ↓
1. 直前 Revision のデータを読み込む
2. 変化リストを適用（方法 A or B）:
     A. SF 連携（将来）: SuccessFactors から差分データを自動取得
     B. 手動入力（初期）: 管理者が入社・退社・異動リストを CSV/Excel でアップロード
3. 変化サマリーを確認画面で表示:
     「入社 12名 / 退社 3名 / 異動 8名 / Prev 更新あり 8行」
4. 管理者が確認・承認 → 3月 Round のベースデータが確定
5. 担当者に「前回 Revision からの変化点あり」フラグ付きで委任
```

**4月移行後の Round（組織コードが変わるケース）**:

組織の抜本的な変更（新設・廃止・改称・分割・統合）は4月に集中する。1月・3月 Round では旧コードのまま作業する（90%以上が旧コードで問題なし）。4月以降に旧コードが廃止された場合のみ、以下の対応が必要となる。

- 管理者が旧コード → 新コードのマッピングを登録
- 廃止組織に紐づく行に「要確認」フラグ → 担当者が新組織へ手動で移動
- 新設組織への行は新規追加として扱う

**組織構造**（`Organization`）とは:  
SF が管理する組織の木構造全体（組織コード・名称・親子関係）。`AllocationRow.departmentCode` はここを参照する。`beforeOrganizations`（旧構造）と `afterOrganizations`（新構造）として Round に保持する。

### 3-7. Git との比較：採用する機能・採用しない機能

Git との比較を持ち出した理由は「バージョン管理が時系列で綺麗に切れない」という点が本システムも Git も共通しているから。複数の委任ブランチが並行して進み、差し戻し・修正・再提出が発生しながら最終的に 1 つの Revision に収束する構造は、複数のフィーチャーブランチを merge して main に取り込む Git の流れと本質的に同じ。

| Git の概念 | 本システムでの対応 | 採用 |
|---|---|---|
| タグ付きコミット（main） | Revision（確定版・不変） | ✅ |
| フィーチャーブランチ | Round（申請回）| ✅ |
| 並列ブランチ | 委任ツリー内の複数 Submission ＋ Cross-Round 並列実行 | ✅ |
| コミット | Submission（提出物） | ✅ |
| bottom-up マージ（PR レビュー） | ツリー内マージ：各親ノードが子 Submission を統合・確認 | ✅ |
| コンフリクト解消 | 同一 rowId の競合を「競合 Submission の共通上位取りまとめ担当」が解消。最上位同士のみ管理者が解消 | ✅ |
| `git push --force-with-lease`（差し戻し） | 修正を依頼した親が差し戻し、子が再提出 | ✅ |
| リベース | 組織構造パッチ（進行中 Round への適用） | ✅ |
| 自由なブランチ乱立 | — | ❌（Round に kind・scope・basedOn を持たせて管理）|
| 3-way マージ自動解決 | — | ❌（判断が必要な競合は必ず人が解消）|
| ステージングエリア | — | ❌（Submission が同等の役割）|
| Fork（外部コントリビューター） | — | ❌（委任ツリー内に閉じる）|

## 4. ユーザー種別と権限

### 4-1. 3 つの役割

| 役割 | 誰 | 主な責務 |
|---|---|---|
| **管理者** | HRサービス部門 | SF 連携、Round 作成・ベースデータ整備、委任ツリー全体の監視、最終提出（Revision 確定） |
| **取りまとめ担当** | HR担当（部門ごと） | 管理者から委任を受け、直接編集 or 職場への委任。配下 Submission をとりまとめてマージ確認・提出 |
| **担当者** | 職場の部門長、または部門長から委譲されたメンバー | 取りまとめ担当から委任を受け、指定範囲を編集して Submission を提出 |

> **委任は無制限に深くできる**（管理者 → A → B → C → …）。各ノードは受けた範囲内でしか委任できない。委任ツリーの全 Submission が完了して初めて、最上位が提出できる。

### 4-2. 管理者の権限

| 権限 | 内容 |
|---|---|
| Round 作成 | Excel インポートまたは SF 連携で新規 Round（申請回）を作成 |
| Revision 管理 | Round の最終提出を受けて Revision を確定。過去 Revision の参照・比較 |
| Round ベースデータ整備 | 直前 Revision + 期間中の変化（入退社・異動）を適用して次 Round のベースを生成 |
| 組織コードマッピング登録 | 4月移行時の旧→新コードマッピングを登録 |
| 全行閲覧・編集 | 担当フィルタなしで全行にアクセス可能 |
| 委任（取りまとめ担当へ） | 担当領域（組織・階層・条件）と依頼コメントを指定して委任 |
| Cross-Round マージ | 並列 Round の変更を統合。最上位同士のコンフリクト解消 |
| 提出状況管理 | 委任ツリー全体の Submission 状況を一覧確認 |
| 差し戻し | 取りまとめ担当の Submission を差し戻して再編集を依頼 |
| 整合チェック実行 | 出向・兼務の自動チェック、統計的異常検出 |
| 最終提出（Revision 確定） | Round 全体を確定して新 Revision を生成 |
| Excel エクスポート | Revision 全体または部分を Excel に出力 |
| ユーザー管理 | アカウント・権限・ポリシーの設定 |
| SF 連携 | SuccessFactors からのデータ取り込み・完成データの書き戻し |

### 4-3. 取りまとめ担当の権限

| 権限 | 内容 |
|---|---|
| 担当範囲の閲覧・編集 | 委任された範囲の全行を編集可能（自分の Submission） |
| 担当者への委任 | 範囲内でさらに担当者へ委任（領域指定＋依頼コメント）|
| ポジション追加・人追加 | 担当範囲内でポジション・人の新規追加が可能 |
| マージ結果確認 | 配下の Submission が全員揃ったら、合算結果を確認して提出 |
| コンフリクト解消 | 自分の配下 Submission 間の競合を解消（共通上位取りまとめ担当として） |
| 差し戻し | 配下の Submission を差し戻して再編集を依頼（コメント付き） |
| 提出（Submission 完了） | 委任先全員の Submission が完了・マージ確認が終わったら自分の Submission を提出 |
| Excel エクスポート/インポート | 担当範囲を Excel に出力し、修正後にアップロードして反映 |
| 委任状況の確認 | 配下の担当者の Submission 状況をツリー表示で確認 |

### 4-4. 担当者の権限

| 権限 | 内容 |
|---|---|
| 委任範囲の閲覧・編集 | 委任された範囲のレコードのみ編集可能 |
| ポジション追加・人追加 | 委任範囲内でポジション・人の新規追加が可能 |
| 提出（Submission 完了） | 委任された範囲の編集完了を提出 |
| Excel エクスポート/インポート | 担当範囲を Excel に出力し、修正後にアップロード |
| ポジション申請 | 新規ポジションコードの払い出しを申請 |

### 4-5. 権限の技術実現方式（ポリシーベース）

行レベルのアクセス制御は「ユーザー側にアクセス範囲ポリシーを定義」する方式を採用する。

```
例:
  ユーザー A（Level 3以上担当）  → orgLevel >= 3 の行が編集可
  ユーザー B（HR担当）           → orgCode IN ('HR01','HR02') の行が編集可
  ユーザー C（出向管理担当）     → concurrentType = '出向' の行が編集可
```

- 重複する行（複数ポリシーに該当）は、該当するすべてのユーザーに表示される
- 並列 Round でも同じポリシーが適用される（コンフリクトはマージ時に検出）
- ad-hoc な付け替えは DB 側の override で対応し、Excel フォーマットには反映しない

### 4-6. 組織コードの旧/新表示

リスト上の `departmentCode` は基本的に旧コード（1月・3月 Round は90%以上が旧コードのまま）。一方、Level 3以上の組織は新コード・新名称で語られることが多く、表示上の認識ズレが生じやすい。

**対応方針**:

- **表示**: `departmentCode`（旧コード）はそのまま保持し、組織名はその Round の `beforeOrganizations` マスタから引く。4月以降の `afterOrganizations` が利用可能な場合は、新旧の組織名を並記する（例: `技術本部（旧: 情報システム本部）`）
- **UI**: 担当者が「組織名で検索」したとき、旧名・新名どちらでもヒットするようにする
- **4月移行時のみ**: 管理者がコードマッピングを登録することで、旧コード行を新コードに移行できる（§3-6 参照）

### 4-7. 出向・兼務の相手方情報（クロス Submission 参照）

担当者が編集中の行に `concurrentType`（出向・出向受入・兼務）がある場合、対になるポジション・職務情報を参照できると整合確認が容易になる。

**表示仕様**:

```
行: 山田 太郎 / 出向 / HR01（出向元）

  [相手方情報パネル]
  ─────────────────────────────────────────────────────
  出向先: TEC01（技術本部）
  positionCode: P10234  |  band: 4  |  officialPosition: 部長
  ─────────────────────────────────────────────────────
  データ出典: ● Rev.3 確定版（2026-01 確定）
              ○ 1月版 Round 進行中（鈴木さん担当 / 未提出）

  [鈴木さんに照会する]  [出向先と自分の行を並べて確認]
```

- **表示する項目（限定）**: positionCode・band・officialPosition・departmentCode。個人情報に踏み込まない範囲で整合確認に必要な項目のみ
- **データ出典の明示**: 確定版（Revision）か、進行中 Round の最新値かを必ず表示する
- **照会アクション**: 相手方の担当者に行レベルの確認依頼を送る（§9-1 の照会機能と統合）
- **最小開示の原則**: 相手方の Submission 全体は見えない。パネルに表示する項目のみ開示

## 5. 階層別担当と自動ポジション共有

### 5-1. 階層別担当が発生する構造

同じ組織に対して、担当する「階層レベル」が異なる複数の担当者が存在する。これは「親子」関係ではなく、**同じ管理者から委任を受けた兄弟担当者**の関係。

```
管理者
  ├── 鈴木さん（取りまとめ担当）: orgLevel >= 3 の行を担当
  │     → 本部長・部長ポジションの新設・変更（新組織カットで編集）
  │     → Prev をベースにするのではなく、新組織の構造で直接記入
  └── 佐藤さん（担当者 A）: 営業第1課（orgLevel <= 2）を担当  ←┐ 兄弟
      伊藤さん（担当者 B）: 営業第2課（orgLevel <= 2）を担当  ←┘
        → Prev（前回 Revision）をベースに after を記入
        → 鈴木さんが作ったポジションコードを参照してメンバーをアサインする
```

**課題（現状）**: 鈴木さんが P12345 を作ると、佐藤さん・伊藤さんはコードをメールや口頭で知らないとアサインできない。兄弟担当者間のこの手渡しが属人化している。

**兄弟間でやり取りが必要になるケースの約90%は、グループ社員 ID が複数行に跨っているケース**。同一人物（グループ社員 ID が一致）が出向元・出向先、または本務・兼務として複数の担当者の行に存在するため、兄弟担当者がそれぞれ編集した結果を突き合わせて整合性を確認する必要がある。確認観点は氏名・band・officialPosition 等「同一人物であれば一致するべき項目」の一致確認が中心。

### 5-2. ToBe：ポジションコードの自動共有（兄弟担当者間）

```
鈴木さんが P12345 を新規作成（営業本部 / Level 3 部長ポジション）
  ↓ システムが「同 Round・同組織スコープを持つすべての担当者」を特定
  ↓ 佐藤さん・伊藤さんへ通知: 「営業本部に新ポジション P12345（部長）が作成されました」
  ↓ 佐藤さん・伊藤さんの編集画面で P12345 が即時参照可能（手渡し不要）
  ↓ ドロップダウンで P12345 を選択してメンバーをアサインできる
```

- 共有されるのは「同じ Round の同じ組織スコープを持つすべての担当者」（委任ツリーの上下関係は問わない）
- 空席ポジションとして作成されるため、各担当者が自分の組織のメンバーをアサイン可能
- **Level 3以上の担当者は新組織カットで編集**するため、Prev 値をそのまま引き継ぐのではなく新しい組織構造に直接記入する点に注意

## 6. 認証・ログインフロー

### 6-1. 想定認証方式

本番環境では **SAML 2.0 による SSO** を前提とする（社内 AD / Azure AD など IdP は未定）。

```
フロントエンド
  → GET /api/auth/login
  → IdP（SAML）にリダイレクト
  → 認証成功 → サーバーが SAML レスポンスを受け取り Cookie 発行
  → メールアドレスで users テーブルを照合 → ロール確認
```

### 6-2. 環境変数による動作モード切り替え

STEP1 と STEP2 は**アプリシェル（画面動線）が根本的に異なる別物**として設計する。環境変数で切り替える。

| `VITE_APP_MODE` | `VITE_AUTH_MODE` | 用途 |
|---|---|---|
| `step1` | `none` | STEP1 本番（Excel ローカル運用・認証なし・別動線）|
| `step2` | `stub` | STEP2 DEV（SQLite + X-User-Id スタブ認証）|
| `step2` | `sso` | STEP2 本番（Aurora + SAML SSO）|

**STEP1 の動線**: ファイル選択 → モード選択 → 編集キャンバス → Excel エクスポート（認証画面なし）  
**STEP2 の動線**: SSO ログイン → ポータル（依頼一覧）→ 委任詳細 → 編集キャンバス → 提出

### 6-3. ロール判定とログイン後の遷移

```
SSO ログイン（メールアドレス確認）
  → role = 'admin'         → Round 一覧・管理ダッシュボードへ
  → role = 'coordinator'   → 依頼一覧（取りまとめ担当ポータル）へ
  → role = 'member'        → 依頼一覧（担当者ポータル）へ
  → 未登録ユーザー         → アクセス拒否（管理者への招待依頼案内を表示）
```

## 7. 管理者フロー：Round 作成から委任まで

### 7-1. Round の作成

1. 管理者が「新規 Round（申請回）を作成」を選択
2. Round 名（例: `2026年度 1月版`）・kind（`annual` / `patch`）・発令予定日を入力
3. ベース Revision を選択（通常は最新 Revision が自動選択される）
4. **方法 A**: Excel ファイルをアップロード → サーバーが `AllocationRow[]` に変換して DB 保存
5. **方法 B**: SuccessFactors 連携で直接取り込み（SF 連携実装後）
6. Round 作成後、委任ウィザードへ進む

3月版は「前回 Revision をベースに作成」が推奨（1月版の確定状態が引き継がれる）。

### 7-2. 取りまとめ担当への委任

管理者は「委任」操作で担当領域と依頼コメントをセットして Submission を作成する。

```
委任の指定方法:
  A. 組織単位     → 「営業本部（orgCode: EIG01）配下の全行」
  B. 階層フィルタ → 「orgLevel >= 3 の行のみ」（Level 3以上は新組織カット）
  C. 条件指定     → 「出向・兼務フラグのある行のみ」
  D. 手動選択     → レコードリストから個別にチェックボックスで選択

依頼コメント例:
  「3月末の人事異動を反映してください。
   新入社員 3名（別紙参照）への配置をお願いします。
   提出期限: 1/31」
```

> **依頼コメントに書かないこと**: 「ポジションはXXを使ってください」は通常不要（ポジションプールから担当者が自動採番）。「band を一致させてください」も不適切——整合チェックは別担当者と協議して調整するものであり、委任時点では正解値が確定していない。

- 1 つの Round に対して複数の取りまとめ担当に委任可能
- 同じ行に複数の Submission が重複することもある（並列 Round でコンフリクトとして検出される）
- 委任後、システムが取りまとめ担当へメール通知（URL 付き）

### 7-3. 通知メールのイメージ

```
件名: 【要員配置システム】「2026年度1月版」編集依頼のご連絡

田中 様

2026年度1月版 Round の編集依頼が届いています。

■ 担当領域: 人事本部（HR01〜HR03）計 52 行
■ 提出期限: 2026年1月31日
■ 依頼コメント:
  3月末の人事異動を反映してください。
  新入社員 3名（別紙参照）への配置をお願いします。

ログイン後、「依頼一覧」から本 Round をクリックしてください。
https://hr-allocation.company.internal/

（自動送信メールです）
```

## 8. 取りまとめ担当・担当者フロー

### 8-1. 依頼一覧（ポータル画面）

ログイン後に表示。管理者・取りまとめ担当・担当者で共通。

```
依頼一覧
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 Round 名                 担当範囲      行数  Submission状態  期限
─────────────────────────────────────────────────────────────
 2026年度1月版 [進行中]   人事本部      52行  ✎ 編集中        1/31
 2025年度3月版 [完了]     人事本部      49行  ✓ 提出済み      ─
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

依頼コメント（2026年度1月版）:
  「3月末の組織改編（新設: HR推進室）を反映してください…」
```

### 8-2. 担当者への委任（Submission の分割）

取りまとめ担当は、自分の Submission の範囲をさらに細かく担当者へ委任できる（Submission が子 Submission を持つ）。

```
委任画面（取りまとめ担当が操作）:

  委任先: [山田 花子（担当者）▾]
  担当範囲: ○ 組織単位  ● 手動選択  ○ 条件指定
  対象行: ☑ HR推進室（5行）  ☑ HR支援課（8行）
  依頼コメント: 「HR推進室の新メンバー配置と、退職者行の削除をお願いします。
               ポジションはプールから採番してください。」
  [委任する]
```

- 委任した行は取りまとめ担当には読み取り専用（担当者が提出するまで）
- 委任先の Submission が完了するまで、委任元は自分の Submission を提出できない
- 委任は無制限に深くできる（担当者がさらに別の担当者へ委任することも可能）

### 8-3. 編集方法：Web 編集と Excel 編集の併用

すべてのロール（管理者・取りまとめ担当・担当者）は、編集方法として以下の 2 つを選べる。

**方法 A: Web 編集**

- STEP1 と同じ編集 UI を使用（組織パネル表示・Undo/Redo・AI アシスタントなど）
- データの保存先がサーバー DB になるだけで操作感は変わらない
- 整合エラー通知バナーがリアルタイムで表示される

**方法 B: Excel エクスポート → 修正 → アップロード**

- 担当範囲を Excel にエクスポートしてローカルで編集
- エクスポート時に `rowId`（システム内部 ID）が非表示列として付与される
- アップロード前に必ず **diff プレビュー** を表示する（「3行更新・2行追加」などを確認してから適用）
- Web 編集と組み合わせも可能

**行の照合ルール（Excel 再アップロード時）**

| 状況 | 照合方法 | 扱い |
|---|---|---|
| `rowId` あり | rowId で 1:1 照合 | 該当行を上書き更新 |
| `rowId` なし（Excel で手動追加した行） | 照合しない | 新規追加として扱う |
| `rowId` あり、担当スコープ外 | — | 警告を出して適用をブロック |

> 新規追加行の重複候補（名前＋組織コードが完全一致する行が既に存在）は diff プレビュー時に警告。最終判断は担当者が行う。

### 8-4. 提出フロー（Submission の完了）

```
担当者 or 取りまとめ担当が「提出」ボタンを押す
  → 担当範囲の最終バリデーション実行
  → エラーあり: エラー一覧を表示し提出をブロック
  → ワーニングのみ: 「ワーニングがあります。提出しますか？」確認ダイアログ
  → 問題なし or 確認OK:
      → Submission ステータスを「提出済み」に変更
      → 委任元（取りまとめ担当 or 管理者）に通知「〇〇さんが提出しました」
      → 提出後は編集不可（再編集は委任元から差し戻し）

取りまとめ担当の提出の前提条件:
  → 自分が委任した子 Submission がすべて「提出済み」
    （または個別に「強制完了」を選択して上書き可能）
```

## 11. 管理者フロー：収集・整合確認・最終提出

### 11-1. 提出状況ダッシュボード（委任ツリー表示）

### 11-2. 並列 Round のマージ

複数の Round（例: `2026年度1月版` と `HR緊急修正`）がどちらも完了状態になったとき、管理者が Cross-Round マージを実行する。

```
マージ実行
  → Round A と Round B の変更を rowId 単位で突き合わせる
  → 非重複行（片方だけが変更）: 自動マージ ✅
  → 重複行（両方が同じ行を変更）: コンフリクト一覧に表示 🔴
      → 競合した行を担当していた両 Round の上位取りまとめ担当に解消を依頼
      → 最上位同士（管理者直下）の競合は管理者が判断
  → 全解消後 → 新 Revision として確定
```

### 11-3. 整合性チェック（自動）

| チェック種別 | 内容 |
|---|---|
| 出向・兼務の一致確認 | 同一グループ社員 ID を持つ行（出向元/出向先、本務/兼務）間で、「同一人物であれば一致すべき項目」が一致しているかチェック。確認観点：氏名・band・officialPosition など複数項目。担当者が異なるため、一方が更新しても他方が追随しない場合に検出する。 |
| バリデーションエラー | A〜G 系バリデーション（必須フィールド・コードリスト逸脱など）|
| 統計的異常検出 | 昇進率・降格率・異動数が過去 Revision から統計的に外れていないか |
| 未提出 Submission の確認 | 提出が完了していない Submission の一覧 |

### 11-4. 差し戻し

```
差し戻し操作（取りまとめ担当または管理者が実行）:
  → 直接の委任元ノードのみが差し戻せる（飛ばしての差し戻しは不可）
  → コメント必須（何が問題か・どう直すべきか）
  → 対象 Submission のステータスを「差し戻し」に変更
  → 差し戻された担当者に通知
  → 担当者が修正して再提出
  → 差し戻し元（委任元）に「再提出完了」の通知
```

### 11-5. 最終提出（Revision 確定）

```
管理者が「最終提出」を実行
  → 全 Submission の最終バリデーション
  → コンフリクト未解消がある場合: ブロック（強制オプションあり ← 要業務確認）
  → 成功:
      → Round ステータスを「完了」に変更
      → 新しい Revision を作成（例: `Rev.4 2026年1月版 確定`）
      → Excel エクスポートが可能（HR システム入力用）
      → SuccessFactors への書き戻し（SF 連携実装後）
```

## 12. 通知システム

| イベント | 通知先 |
|---|---|
| Round への委任（Submission 作成） | 該当の取りまとめ担当 |
| 子 Submission の委任 | 該当の担当者 |
| 整合エラーの検出 | 関係する両 Submission 担当者 |
| 新規ポジション作成（同組織の別担当へ） | 同 Round・同組織の担当者 |
| ポジション申請の承認 | 申請担当者 |
| Submission の提出完了 | 委任元 |
| 差し戻し | 差し戻された担当者（委任を受けた者）|
| 照会・確認依頼の受信（出向/兼務相手方含む） | 依頼先担当者 |
| 照会への返信 | 依頼元担当者 |
| Round ベースデータ整備完了 | 委任先の取りまとめ担当 |
| 4月移行：組織コード変更の影響行あり | 影響を受ける行の担当者 |
| Cross-Round コンフリクト発生 | 競合行の上位取りまとめ担当（最上位同士の場合は管理者）|
| 最終提出完了（Revision 確定） | 全関係者（任意）|

通知チャネル: **メール**（基本）＋ **システム内通知バッジ**

## 14. 非機能要件

| 項目 | 要件 |
|---|---|
| **スケール** | 最大約 3 万行（人・ポジション各 3 万規模）の 1 Round を扱える |
| **並列処理** | 複数 Round が同時進行しても、ポリシーベース行分離により通常は競合しない |
| **パフォーマンス** | Submission の行一覧表示は 3 秒以内。提出時バリデーションは担当範囲のみ |
| **セキュリティ** | Submission 範囲外の行の値は API レスポンスに含めない（サーバーサイドでフィルタ）|
| **情報セキュリティ** | 出向・兼務の整合確認は最小開示の原則。相手の行全体は開示しない |
| **可用性** | 年 2 回の発令期間中は高可用性が必要（Aurora Multi-AZ を想定）|
| **後方互換** | STEP1 の Excel フォーマットをそのまま import できること |

## 15. 移行計画（STEP1 → STEP2）

### フェーズ 1（STEP2 初期）

- SQLite ローカルサーバーで STEP2 機能をデモ実装（F-01〜F-17）
- スタブ認証（`VITE_AUTH_MODE=stub`）で全機能を試験運用
- Aurora 接続・SAML アダプタ差し替えで本番化

### フェーズ 2（STEP2 強化）

- F-21〜F-26 の実装
- SAML 接続の実装（IdP 選定後）
- 担当者向けトレーニング資料の整備

### フェーズ 3（Web ファースト）

- Excel を「出力専用フォーマット」に
- 改版管理・変更履歴が Web で完結

### STEP1 との並走方針

- STEP1（`VITE_APP_MODE=step1`）は STEP2 移行後も維持
  - サーバーに接続できない環境での緊急対応用
  - ただし STEP2 本番稼働後は新機能開発は STEP2 側に集中
