# 12 — STEP2 サービス要件定義

> **ステータス**: ドラフト（2026-06）
> **用途**: チームメンバー・企画書向けのイメージ合わせ用。ToBe の業務フロー・ルール・機能要件を記述する。
> STEP1（Excel ローカル運用）は `docs/01-requirements.md` 参照。Round/Submission の DB データモデル・3-way merge の実装詳細は `docs/14-delegation-model.md`（現行の正）を参照。本書は業務フロー・要件が中心。

---

## 1. 背景：STEP1 の限界と STEP2 が解決すること

STEP1 は「ブラウザ完結・サーバーなし」で動作する Excel 補助ツールとして、操作の可視化・Undo/Redo・AI 支援などの価値を提供してきた。一方で Excel をデータの受け渡し媒体にする構造上、以下の課題が本質的に解決できない。

| 課題 | 具体的な影響 |
|---|---|
| 担当者間の照合が手作業 | 出向元・出向先の band 一致をメールや Excel で手渡し確認している |
| 矛盾の発見が遅い | マージ後にしか整合エラーが見えない |
| ポジション番号の属人化 | 採番ルールが暗黙知。別担当者へのコード共有がメールや口頭で手作業 |
| 改版・変更通知がない | ファイルを上書き保存するため誰がいつ何を変えたか追えない |
| 担当者間のやり取りが非構造 | 依頼・確認がセル内テキスト・メール等に分散 |
| 組織構造変更への追随が手作業 | 4月直前まで組織が変わるたびに各担当への影響確認・通知を手動で行っている |

STEP2 は「中央 DB（Aurora）＋ Web 編集＋ SSO 認証」を導入することで、これらを構造的に解決する。

## 2. ToBe 業務フロー全体像

STEP1 現状（Excel 抽出 → 分割配布 → メール返送 → 手動マージ → メール往復での整合確認 → 最終 Excel 登録、§1 参照）に対する ToBe フロー:

```
  管理者
    ↓ SF から抽出 or Excel インポートで Round（申請回）を作成・ベースデータ整備
    ↓ 取りまとめ担当ごとに担当領域を指定して委任依頼（コメント付き）
    ↓ システムが取りまとめ担当へメール通知（URL付き）

  取りまとめ担当（HR担当・部門ごと）
    ↓ SSO ログイン → 依頼一覧で自分の担当範囲と依頼コメントを確認
    ↓ 直接編集して提出 or 範囲を絞って職場の部門長等へ委任（コメント付き）
    ↓ ポジション新設・人追加も可能。作成したポジション番号は関係担当へ自動共有
    ↓ 配下全 Submission 完了後、自分もマージ確認して「提出」

  担当者（職場の部門長または委譲先メンバー）
    ↓ SSO ログイン → 委任された範囲と依頼コメントを確認
    ↓ Web 編集 or Excel エクスポート→修正→アップロード
    ↓ 「提出」（自分の Submission を完了）

  管理者
    ↓ 提出状況ダッシュボードで進捗管理・差し戻し（コメント付き）
    ↓ 整合チェック（出向・兼務の自動検出）・統計的異常確認
    ↓ 最終提出 → Round を確定（closed）→ SF 登録。確定した Round が次 Round のベースになる
```

## 3. データモデル：Round / Submission の概念

> DB テーブル構造（`allocation_rows` / `submission_rows` 等）・3-way merge アルゴリズムの詳細は `docs/14-delegation-model.md` を参照。本節は ToBe 業務フローに必要な概念定義のみ扱う。

### 3-1. 3 つの概念

| 概念 | 日本語名 | 定義 | Git での類似概念 |
|---|---|---|---|
| **Revision**（概念上） | 改訂版 | SF に反映された（または反映予定の）正式確定状態を指す**概念**。DB 上の独立テーブルとしては実装しない — `allocation_rows` を持つ「確定（closed）」状態の Round がこれに相当する（判断根拠は §13「実装しない機能」参照） | タグ付きコミット |
| **Round** | 申請回 | ある確定状態から次の確定状態を作るための作業単位。年 2 回（1月・3月）が基本。委任ツリーを構成する複数の Submission を束ねる | フィーチャーブランチ |
| **Submission** | 提出物 | Round 内で 1 人の担当者が担当範囲を編集して提出した変更のまとまり。委任ツリーの 1 ノード | コミット |

単一 Round 内の委任ツリー（bottom-up にマージが進む）:

```
Round A（2026年1月版）
  ├── 管理者（発行者・確定者）
  │     ├── 田中さん（取りまとめ・人事本部）← マージ結果確認者
  │     │     └── 山田さん（担当者・HR推進室）
  │     ├── 鈴木さん（取りまとめ・技術本部）← マージ結果確認者
  │     │     ├── 佐藤さん（担当者・技術2課）
  │     │     └── 伊藤さん（担当者・技術3課）
  │     └── …
  └── 全ツリー完了 → Round を確定（次の Round のベースになる）
```

**役割分担**（委任ツリーの各段で bottom-up に発生）: 委任を出した親ノードが「マージ結果確認者」となり、直接の委任先が全員提出したら合算結果を確認する。問題を自分のスコープで解決できなければ子を差し戻す（**修正者**）。同じ行を複数の子が変更した場合はその共通上位取りまとめ担当が**コンフリクト解消者**となる（最上位同士の競合のみ管理者が解消）。管理者は全 Submission 集約後の**確定者**。

### 3-2. Round・Submission の性質

| 属性 | 説明 |
|---|---|
| Round `basedOn` | 直前の確定（closed）Round を必須で参照 |
| Round `kind` | `'annual'`（年次・年2回、深い委任ツリー）or `'patch'`（局所修正・浅い委任ツリー、随時発生） |
| Round ライフサイクル | `draft` → `in_progress` → `ready` → `merged` → 確定（closed） |
| Submission | 委任ツリーの 1 ノード（担当者 1 人 × 担当範囲 × Round）。変更内容 = Row の差分リスト |
| Submission ステータス | `pending → in_progress → submitted → merged`（または `revision_requested` で差し戻し、強制提出時は `cancelled`）。詳細は `docs/14-delegation-model.md` §2-3 |

「Round の外にある変更」は存在しない——すべての変更は必ずいずれかの Round を経由して次の確定状態に反映される。委任先の Submission がすべて完了（`merged`/`cancelled`）にならないと、委任元は自分の Submission を提出できない。

### 3-3. ツリー内 bottom-up マージ

1 つの Round でも、委任ツリー全体が完了するまで時系列は綺麗に切れない。異なるブランチ（人事本部系・技術本部系…）は独立して並行して進むため、あるブランチが完了しても別ブランチは編集中ということが当然起きる。各親ノードは「自分の直接の子が全員揃ってから」マージ確認を開始し、競合があれば共通上位取りまとめ担当が解消（解消できなければ差し戻して再提出を依頼）。修正が確定すると、その差分は親・親の親へと順次積み上がっていく。全グループ会社に影響するデータ（band・組織コード等）は、最終的に管理者が確認する最上位でのみ全体整合が保証される。

> **Round 間の自動マージ（Cross-Round マージ）は実装しないことを決定済み**。Round は年2回（1月・3月）で固定であり並列実行が業務上発生しないため。判断根拠は §13「実装しない機能」参照。

### 3-4. Round ベースデータの整備（前回確定状態からの引き継ぎ、F-22）

新しい Round を作成するとき、直前の確定 Round のデータをそのまま「before（Prev）値」として使えない場合がある。確定から次の Round 開始までの間に、実際の人員・組織が変化しているため。1月版 + 期間中の変化差分（入社・退社・異動・出向の開始終了）から 3月版のベースをシステムが生成し、「入社 12名 / 退社 3名 / 異動 8名」のようなサマリーを管理者が確認・承認する。

**4月移行**: 組織の抜本的な変更（新設・廃止・改称・分割・統合）は4月に集中する。1月・3月 Round では旧コードのまま作業する（90%以上が旧コードで問題ない）。4月以降に旧コードが廃止された場合のみ、管理者が旧→新コードのマッピングを登録し、廃止組織に紐づく行に「要確認」フラグを立てて担当者が新組織へ手動で移動する。

### 3-5. Git との比較：採用する機能・採用しない機能

| Git の概念 | 本システムでの対応 | 採用 |
|---|---|---|
| タグ付きコミット（main） | Round の確定（closed）状態 | ✅（独立 Revision テーブルとしては不採用） |
| フィーチャーブランチ / コミット | Round / Submission | ✅ |
| bottom-up マージ（PR レビュー） | 各親ノードが子 Submission を統合・確認 | ✅ |
| コンフリクト解消 | 同一 rowId の競合を「競合 Submission の共通上位取りまとめ担当」が解消 | ✅ |
| 差し戻し（`--force-with-lease` 相当） | 修正を依頼した親が差し戻し、子が再提出 | ✅ |
| 並列ブランチの merge（Cross-Round マージ） | — | ❌（Round が年2回固定のため発生しない。§13 参照） |
| 3-way マージ自動解決・Fork | — | ❌（判断が必要な競合は必ず人が解消／委任ツリー内に閉じる） |

## 4. ユーザー種別と権限

### 4-1. 3 つの役割

| 役割 | 誰 | 主な責務 |
|---|---|---|
| **管理者** | HRサービス部門 | SF 連携、Round 作成・ベースデータ整備、委任ツリー全体の監視、最終提出（Round 確定） |
| **取りまとめ担当** | HR担当（部門ごと） | 管理者から委任を受け、直接編集 or 職場への委任。配下 Submission をとりまとめてマージ確認・提出 |
| **担当者** | 職場の部門長、または部門長から委譲されたメンバー | 取りまとめ担当から委任を受け、指定範囲を編集して Submission を提出 |

> **委任は無制限に深くできる**（管理者 → A → B → C → …）。各ノードは受けた範囲内でしか委任できない。委任ツリーの全 Submission が完了して初めて、最上位が提出できる。

### 4-2. 権限マトリクス

| 権限 | 管理者 | 取りまとめ担当 | 担当者 |
|---|---|---|---|
| 担当範囲の閲覧・編集 | 全行 | 委任された範囲 | 委任された範囲 |
| ポジション追加・人追加 | ✓ | 範囲内で可 | 範囲内で可 |
| 担当者への委任 | ✓（取りまとめ担当へ）| ✓（範囲内でさらに委任）| ✗ |
| Round 作成・ベースデータ整備 | ✓ | ✗ | ✗ |
| マージ結果確認・コンフリクト解消 | ✓（最上位同士） | ✓（自分の配下 Submission 間・共通上位として） | ✗ |
| 差し戻し | ✓ | ✓（自分の配下のみ） | ✗ |
| 提出（Submission 完了） | ✓ | ✓（配下が完了・マージ確認後） | ✓ |
| Excel エクスポート/インポート | Round 全体 | 担当範囲 | 担当範囲 |
| ポジション申請 | 採番も可 | 申請 | 申請 |
| 提出状況管理・整合チェック実行 | 委任ツリー全体 | 配下のみツリー表示 | ✗ |
| 最終提出（Round 確定）・組織コードマッピング登録・ユーザー管理・SF 連携 | ✓ | ✗ | ✗ |

### 4-3. 権限の技術実現方式（ポリシーベース）

行レベルのアクセス制御は「ユーザー側にアクセス範囲ポリシーを定義」する方式を採用する（例: `orgLevel >= 3` の行が編集可、`orgCode IN (...)` の行が編集可、`concurrentType = '出向'` の行が編集可、など）。重複する行（複数ポリシーに該当）は該当するすべてのユーザーに表示される。ad-hoc な付け替えは DB 側の override で対応し、Excel フォーマットには反映しない。

### 4-4. 組織コードの旧/新表示

`departmentCode` は基本的に旧コード（1月・3月 Round は90%以上が旧コードのまま）だが、Level 3以上の組織は新コード・新名称で語られることが多く、表示上の認識ズレが生じやすい。表示は `departmentCode`（旧コード）をそのまま保持し、組織名はその Round の `beforeOrganizations` マスタから引く。4月以降は `afterOrganizations` があれば新旧の組織名を並記する（例: `技術本部（旧: 情報システム本部）`）。検索は旧名・新名どちらでもヒットさせる。4月移行時のみ管理者がコードマッピングを登録して旧コード行を新コードに移行できる（§3-4 参照）。

### 4-5. 出向・兼務の相手方情報（クロス Submission 参照、F-24）

担当者が編集中の行に `concurrentType`（出向・出向受入・兼務）がある場合、対になる行の **positionCode・band・officialPosition・departmentCode** を限定表示するパネルを参照できると整合確認が容易になる（個人情報に踏み込まない範囲）。データ出典（確定済みか進行中 Round の最新値か）を必ず明示する。**最小開示の原則**: 相手方の Submission 全体は見えない。パネルに表示する項目のみ開示。

## 5. 階層別担当と自動ポジション共有

### 5-1. 階層別担当が発生する構造

同じ組織に対して、担当する「階層レベル」が異なる複数の担当者が存在する。これは「親子」関係ではなく、**同じ管理者から委任を受けた兄弟担当者**の関係（例: 鈴木さんが `orgLevel >= 3` の本部長・部長ポジションを新組織カットで新設・変更する一方、佐藤さん・伊藤さんは `orgLevel <= 2` の各課を Prev ベースで担当し、鈴木さんが作ったポジションコードを参照してメンバーをアサインする）。

**課題（現状）**: 鈴木さんが P12345 を作ると、佐藤さん・伊藤さんはコードをメールや口頭で知らないとアサインできない。この手渡しが属人化している。やり取りが必要になるケースの約90%は、グループ社員 ID が複数行（出向元/出向先、本務/兼務）に跨っているケースで、確認観点は氏名・band・officialPosition 等「同一人物であれば一致するべき項目」が中心。

### 5-2. ToBe：ポジションコードの自動共有（兄弟担当者間）

鈴木さんが P12345 を新規作成すると、システムが「同 Round・同組織スコープを持つすべての担当者」（委任ツリーの上下関係は問わない）を特定して自動通知する。佐藤さん・伊藤さんの編集画面でも即座にドロップダウン選択可能になり、手渡し不要でメンバーをアサインできる。空席ポジションとして作成されるため各担当者が自分の組織のメンバーをアサイン可能。**Level 3以上の担当者は新組織カットで編集**するため、Prev 値をそのまま引き継ぐのではなく新しい組織構造に直接記入する点に注意。

## 6. 認証・ログインフロー

### 6-1. 想定認証方式

本番環境では **SAML 2.0 による SSO** を前提とする（社内 AD / Azure AD など IdP は未定）。フロントエンドが `GET /api/auth/login` から IdP へリダイレクトし、認証成功後にサーバーが SAML レスポンスを受け取って Cookie を発行、メールアドレスで `users` テーブルを照合してロールを確認する。

### 6-2. 環境変数による動作モード切り替え

STEP1 と STEP2 は**アプリシェル（画面動線）が根本的に異なる別物**として設計する。

| `VITE_APP_MODE` | `VITE_AUTH_MODE` | 用途 |
|---|---|---|
| `step1` | `none` | STEP1 本番（Excel ローカル運用・認証なし・別動線）|
| `step2` | `stub` | STEP2 DEV（PGlite + X-User-Id スタブ認証）|
| `step2` | `sso` | STEP2 本番（Aurora + SAML SSO）|

**STEP1 の動線**: ファイル選択 → モード選択 → 編集キャンバス → Excel エクスポート（認証画面なし）
**STEP2 の動線**: SSO ログイン → ポータル（依頼一覧）→ 委任詳細 → 編集キャンバス → 提出

### 6-3. ロール判定とログイン後の遷移

SSO ログイン（メールアドレス確認）後、`role = 'admin'` は Round 一覧・管理ダッシュボードへ、`'coordinator'`/`'member'` はそれぞれの依頼一覧ポータルへ遷移する。未登録ユーザーはアクセス拒否（管理者への招待依頼案内を表示）。

## 7. 管理者フロー：Round 作成から委任まで

### 7-1. Round の作成

1. 管理者が「新規 Round（申請回）を作成」を選択
2. Round 名（例: `2026年度 1月版`）・kind（`annual` / `patch`）・発令予定日を入力
3. ベースとなる直前の確定 Round を選択（通常は最新の closed Round が自動選択される）
4. **方法 A**: Excel ファイルをアップロード → サーバーが `AllocationRow[]` に変換して DB 保存
5. **方法 B**: SuccessFactors 連携で直接取り込み（SF 連携実装後）
6. Round 作成後、委任ウィザードへ進む

3月版は「前回確定状態をベースに作成」が推奨（1月版の確定状態が引き継がれる）。

### 7-2. 取りまとめ担当への委任

管理者は「委任」操作で担当領域と依頼コメントをセットして Submission を作成する。担当領域の指定方法は 4 通り: **A.** 組織単位（例: 営業本部配下の全行）／**B.** 階層フィルタ（例: `orgLevel >= 3` のみ、Level 3以上は新組織カット）／**C.** 条件指定（例: 出向・兼務フラグのある行のみ）／**D.** 手動選択（レコードリストからチェックボックスで個別選択）。

> **依頼コメントに書かないこと**: 「ポジションはXXを使ってください」は通常不要（ポジションプールから担当者が自動採番）。「band を一致させてください」も不適切——整合チェックは別担当者と協議して調整するものであり、委任時点では正解値が確定していない。

1 つの Round に対して複数の取りまとめ担当に委任可能。委任後、システムが取りまとめ担当へメール通知（URL 付き、担当領域・提出期限・依頼コメントを記載）する。

## 8. 取りまとめ担当・担当者フロー

### 8-1. 依頼一覧（ポータル画面）

ログイン後に表示（管理者・取りまとめ担当・担当者で共通の画面）。Round 名・担当範囲・行数・Submission 状態・期限・依頼コメントを一覧表示する。画面レイアウトの詳細は `docs/13-screen-design.md`（S-02 PortalView）参照。

### 8-2. 担当者への委任（Submission の分割）

取りまとめ担当は、自分の Submission の範囲をさらに細かく担当者へ委任できる（Submission が子 Submission を持つ）。委任した行は取りまとめ担当には読み取り専用（担当者が提出するまで）。委任先の Submission が完了するまで、委任元は自分の Submission を提出できない。委任は無制限に深くできる（担当者がさらに別の担当者へ委任することも可能）。

### 8-3. 編集方法：Web 編集と Excel 編集の併用

すべてのロール（管理者・取りまとめ担当・担当者）は、編集方法として以下の 2 つを選べる。

**方法 A: Web 編集** — STEP1 と同じ編集 UI を使用（組織パネル表示・Undo/Redo・AI アシスタントなど）。データの保存先がサーバー DB になるだけで操作感は変わらない。整合エラー通知バナーがリアルタイムで表示される。

**方法 B: Excel エクスポート → 修正 → アップロード** — 担当範囲を Excel にエクスポートしてローカルで編集。エクスポート時に `rowId`（システム内部 ID）が非表示列として付与される。アップロード前に必ず **diff プレビュー** を表示する（「3行更新・2行追加」などを確認してから適用）。Web 編集と組み合わせも可能。

**行の照合ルール（Excel 再アップロード時）**

| 状況 | 照合方法 | 扱い |
|---|---|---|
| `rowId` あり | rowId で 1:1 照合 | 該当行を上書き更新 |
| `rowId` なし（Excel で手動追加した行） | 照合しない | 新規追加として扱う |
| `rowId` あり、担当スコープ外 | — | 警告を出して適用をブロック |

> 新規追加行の重複候補（名前＋組織コードが完全一致する行が既に存在）は diff プレビュー時に警告。最終判断は担当者が行う。

### 8-4. 提出フロー（Submission の完了）

担当者または取りまとめ担当が「提出」を押すと担当範囲の最終バリデーションが走る。エラーがあれば一覧表示してブロック、ワーニングのみなら確認ダイアログを経て提出できる。提出後は Submission ステータスが「提出済み」になり委任元に通知、編集不可になる（再編集は委任元からの差し戻しのみ）。取りまとめ担当は、自分が委任した子 Submission がすべて「提出済み」になっていることが提出の前提条件（または個別に「強制完了」で上書き可能。詳細は `docs/13-screen-design.md` §6 Q-F 参照）。

## 9. 担当者間のオンライン照会・コミュニケーション

### 9-1. 照会機能（F-23）

担当者が「この行についての確認」を別の担当者に送れる（例: 「出向先の組織コードを教えてください」→ 出向先担当者に自動通知 → 画面上で確認・返信 → 照会元に通知）。照会は「行レベル（rowId）」で紐付いており、コンテキストが失われない。**最小開示の原則**: 相手の行全体は見えず、照会したフィールドの値ペアのみ開示。

### 9-2. 整合エラー通知（自動）

出向・兼務で対になる行の band 等が不一致になった場合、両方の Submission 担当者に自動通知する（例: 「Person G001 の band が出向元=4・出向先=3 で一致しません」）。通知から相手に確認依頼を送る、または自社側を修正するアクションを取れる。

---

## 10. ポジション番号管理

### 10-1. ポジションプール（F-21）

新規ポジションコードは中央管理されたプールから払い出す。担当者が組織・役割・等級などを入力して申請 → 管理者に通知（自動採番ルールがあれば即時払い出し）→ 管理者がコードを付与 → 採番完了通知とともに `AllocationRow` に自動反映される（コードを手打ちしない）。

### 10-2. ポジション番号の自動共有（重複担当対応）

§5-2 参照。ポジション新規作成時、同じ組織をスコープに持つすべての担当者（同 Round 内）に自動通知される。

## 11. 管理者フロー：収集・整合確認・最終提出

### 11-1. 提出状況ダッシュボード（委任ツリー表示）

委任ツリーを階層表示し、各 Submission（担当者・範囲・行数・状態・更新日）と全体の完了率・整合エラー件数を一覧できる（管理者向け）。

### 11-2. 整合性チェック（自動）

| チェック種別 | 内容 |
|---|---|
| 出向・兼務の一致確認 | 同一グループ社員 ID を持つ行（出向元/出向先、本務/兼務）間で、「同一人物であれば一致すべき項目」が一致しているかチェック。確認観点：氏名・band・officialPosition など複数項目。担当者が異なるため、一方が更新しても他方が追随しない場合に検出する |
| バリデーションエラー | A〜G 系バリデーション（必須フィールド・コードリスト逸脱など）|
| 統計的異常検出 | 昇進率・降格率・異動数が過去の確定 Round から統計的に外れていないか |
| 未提出 Submission の確認 | 提出が完了していない Submission の一覧 |

### 11-3. 差し戻し

取りまとめ担当または管理者が実行。直接の委任元ノードのみが差し戻せる（飛ばしての差し戻しは不可）。コメント必須。対象 Submission を「差し戻し」に変更して担当者に通知 → 担当者が修正して再提出 → 差し戻し元に「再提出完了」を通知する。

### 11-4. 最終提出（Round 確定）

管理者が「最終提出」を実行すると全 Submission の最終バリデーションが走る。コンフリクト未解消があればブロック（強制オプションあり、`docs/13-screen-design.md` §6 Q-F 参照）。成功すると Round が「完了（closed）」になり `allocation_rows` が確定状態として次 Round のベースに参照される。Excel エクスポート・SuccessFactors への書き戻し（SF 連携実装後）が可能になる。

## 12. 通知システム

| イベント | 通知先 |
|---|---|
| Round への委任（Submission 作成） | 該当の取りまとめ担当 |
| 子 Submission の委任 | 該当の担当者 |
| 整合エラーの検出 | 関係する両 Submission 担当者 |
| 新規ポジション作成（同組織の別担当へ） | 同 Round・同組織の担当者 |
| Submission の提出完了 | 委任元 |
| 差し戻し | 差し戻された担当者（委任を受けた者）|

| 最終提出完了（Round 確定） | 全関係者（任意）|

通知チャネル: **メール**（基本）＋ **システム内通知バッジ**

### 実装しない機能と判断根拠（2026-06）

**F-04 Revision 管理 / F-17 並列 Round マージ**: 実装しない。

- Round は年2回（1月版・3月版）で固定であり、並列実行は業務上発生しない
- 各 Submission の依頼時・提出時にスナップショットが保存されるため、変更の追跡・差分参照はすでに可能
- Revision テーブルが解決しようとした「不変の確定状態」は、Round の `closed` ステータス ＋ Submission のスナップショット連鎖で代替できる
- 並列 Round が不要なため、Cross-Round マージ・共通ベース問題（Revision の最大の存在理由）も発生しない
- 代替: 「直前 Round の確定状態」= `rounds` の最新 closed レコードの `allocation_rows` 参照。過去参照は Submission の `snapshot_data` と diff で実現

## 14. 非機能要件

| 項目 | 要件 |
|---|---|
| **スケール** | 最大約 3 万行（人・ポジション各 3 万規模）の 1 Round を扱える |
| **並列処理** | 複数 Round が同時進行しても、ポリシーベース行分離により通常は競合しない |
| **パフォーマンス** | Submission の行一覧表示は 3 秒以内。提出時バリデーションは担当範囲のみ |
| **セキュリティ** | Submission 範囲外の行の値は API レスポンスに含めない（サーバーサイドでフィルタ）|
| **情報セキュリティ** | 出向・兼務の整合確認は最小開示の原則。相手の行全体は開示しない |
| **可用性** | 年 2 回の発令期間中は高可用性が必要（Aurora Multi-AZ を想定）|
| **後方互換** | STEP1 の Excel フォーマットをそのまま import できること |

## 15. 移行計画（STEP1 → STEP2）

### フェーズ 1（STEP2 初期）

- PGlite ローカルサーバーで STEP2 機能をデモ実装（P0 機能一式。F-04・F-17 除く）
- スタブ認証（`VITE_AUTH_MODE=stub`）で全機能を試験運用
- Aurora 接続・SAML アダプタ差し替えで本番化

### フェーズ 2（STEP2 強化）

- F-21〜F-27 の実装
- SAML 接続の実装（IdP 選定後）
- 担当者向けトレーニング資料の整備

### フェーズ 3（Web ファースト）

- Excel を「出力専用フォーマット」に
- 変更履歴が Web で完結

### STEP1 との並走方針

STEP1（`VITE_APP_MODE=step1`）は STEP2 移行後も維持する（サーバーに接続できない環境での緊急対応用）。ただし STEP2 本番稼働後は新機能開発は STEP2 側に集中する。
