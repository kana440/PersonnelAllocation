PersonnelAllocation · 開発者向け設計案

組織図取込パイプライン
— AIによる組織変更提案の全体設計

組織図の画像・PPTを読み取り、既存の基本操作（EditOperation）へ落とし込むまでの一連の流れをまとめた。 ドメインの構成（基本操作・変更パターン・バリデーション）は一切変更せず、その手前に新しい入力経路を1本足す、という位置づけ。

ロバスト性 — 入力品質に応じて経路が変わる
低ストレス — 確認は少数に絞る
検証可能性 — 各段階を単体でテストできる
資産の切り分け — 新規と既存を分けて示す
Design Principles

設計原則

検討の過程で誤った方向へ進みかけ、修正した7つのポイント。実装時にこの原則から外れていないか都度立ち返る。

1

原子的な単位は「基本操作」であり、導出・バリデーション単体ではない

deriveFieldUpdatesや各バリデーションは、特定のEditOperationのapply()/onFieldChangeの内部でのみ意味を持つ。AIの出力を汎用的に「埋めて検証する」層を新設しない。

2

変更パターン（EditPattern / detect()）は事後的な表示分類器

1行に対して複数同時に真になる、非排他的な集計・表示用の仕組み。「次にどの操作を実行すべきか」を決める前向きの判定には転用しない。

3

AIの出力は常に「操作への入力」

新しいコードのゴールは{operationId, rowId, values}——人がフォームに入力してsubmitするのと同じ形を作ることだけ。実行は既存のexecuteOperation / executeBatchにそのまま渡す。

4

知覚は並列、判定は直列

画像の読み取り（Vision）は互いに独立なので並列化してよい。しかし操作選定は、同一セッション内の前の画像・前の人の提案結果に依存するため、処理順を守って直列に行う。

5

曖昧さは「値」ではなく「複数人で共有される事実」として扱う

組織名や役職の読み取りゆれは、人ごとに個別の問題ではなく、多くの場合1つの事実を複数人が参照している。確認の単位もこれに合わせる。

6

変わっていない人には、何もしない

読み取った内容が現在の行（prevXxx／現在値のいずれとも）と矛盾しなければ、操作を作らない。全員に何か操作を割り当てようとしない。

7

失敗や食い違いは、AIが自動で直さず必ず人に見せる

「自己修復（自動で値を調整して再試行する）」は採用しない。DryRunで検出した問題も、確信度が低い提案も、報酬に関わる提案も、すべて人の確認を経由してから確定する。

Overview

全体パイプライン

4つのグループ（準備・抽出・判定・適用）で構成する。確認（人との対話）は2箇所（確認A・確認B）、それとは別に人が事前に行う宣言（準備-1）とアクション不要の事後提示（適用-2）がある。 操作選定と確認Bの間には、コミットせず検証だけを行うドライラン（判定-5）を挟む。

Why this works

なぜこれが効果的か

検討の過程で出てきた「効きそうな理由」を、各段階の設計と対応づけて整理する。

1

無理に確定させない設計が、精度の低い入力でも壊れない

抽出-1（Vision観測抽出）は自由記述のまま保持し、Enum強制は判定-2（マスタ正規化）以降に限定する。「M」のような曖昧な略記でも、無理な確定や取りこぼしが起きない。

2

共有される事実としてまとめることで、情報を失わずに効率よく解決できる

生テキストを保持したまま複数人で共有される単位（UnresolvedFact）にまとめる。読み取った根拠が最後まで残るのと、1つの事実の解決が全員に波及するのを同時に得ている。

3

確認を2つの粒度に分けたことで、量と質のバランスが取れる

確認Aは「事実」単位（少数の解決で多くの人に波及）、確認Bは「提案」単位（実際に変わる人だけ）。1つの対話に両方を混ぜると、どちらの効率も活かせない。

4

変わっていない人には何もしないことが、レビュー量そのものを減らす

判定-3（変更検知）のno-opゲートにより、確認Bも実行も「本当に変わった人」だけが対象になる。母数を減らすこと自体が、UXにも安全性にも効く。

5

読み取る範囲を資料ごとに事前宣言できる

宣言されなかったフィールドは、既存のprevXxxや各操作自身の導出ロジックにそのまま委ねられる。実フィールド約40個のうち、画像から読み取ろうとする範囲を人が最初に絞れる。

6

判定の材料が、既存の判定パターンをなぞっている

prevXxxと現在値を両方参照する、という判定-3・判定-4の判断材料は、既存の各操作のavailableFor()が既にやっていることと同じ形。新しい判断の枠組みを持ち込んでいない。

7

各段階が独立した純粋関数として検証できる

FieldStateという共通の型を各段階が引き継ぐことで、途中の任意の段階を単体で止めて確認・テストできる。パイプライン全体を通してみないと正しさが分からない、という状態を避けている。

8

上流の誤りは実行を汚さない

適用-1（実行）より手前で何を間違えても、既存のvalidate()/availableFor()/A〜G/W系バリデーションを必ず通る。新しく作る部分の誤りは「悪い提案」で止まり、データの整合性は既存の防御層が保証する。

9

検証は「自動修復」ではなく「人に見せる」形にする

ドライラン（判定-5）で検出した検証エラーや、導出結果と観測の食い違いを、AIが勝手に直さず必ず確認Bへ上げる。DryRunは既存のvalidate()/apply()をコミットせず呼ぶだけなので、新しい判断ロジックを持ち込まない。

10

報酬に関わる項目は、確信度に関係なく必ず人が見る

band/positionBand/payGrade/employmentType/officialPositionCodeは、宣言レベルや自動解決の結果に関わらず確認Bを必ず経由する（MUST_CONFIRM_FIELDS）。

Stage by Stage

各段階の詳細——入出力スキーマ付き

抽出-1・抽出-2・判定-2が扱う曖昧なフィールドは、すべて共通のFieldState<T>という型で表現する。生テキスト・根拠・確信度・解決状態を1つの型が持ち回るので、 途中の任意の時点で「今どこまで分かっているか」を機械的に読めるし、1つのフィールドの解決だけを取り出して単体テストできる。 

// 共通の型: FieldState<T> — 抽出〜判定を通じて同じ器を使い回す
{
  fieldKey: string,
  raw: string,                  // 抽出-1が書き込み、以降不変（根拠として保持）
  evidence: { slideIndex, quote: string, cropRegion?: [x,y,w,h] },
  status: 'raw'|'clustered'|'awaiting_confirmation'|'confirmed'|'auto_resolved',
  value?: T,
  confidence: number,
  source?: 'auto_normalize'|'human_confirm_A'|'domain_derive'
}
準備1

読み取り範囲の宣言

人が事前に宣言

処理を始める前に、この資料が実際にどこまで書かれていそうかを、人が1つ選ぶ。AllocationRowの実フィールド（約40個、prevXxxを除く）を、画像に書かれていそうな度合いで5段階に分けている。 Level4・5はそもそも宣言の対象にせず、常に既存のprevXxx／導出ロジックに委ねる。

Level 1ほぼ確実に読み取れる
lastName firstName ／組織名の生テキスト ／役職・肩書の生テキスト ／上司部下関係（位置関係）
Level 2視覚的な合図があれば
employmentType/concurrentTypeの手がかり ／secondmentFromCompany/secondmentToCompany/concurrentReason ／transferReasonのニュアンス
Level 3資料次第でまれに
location ／jobFamily/jobType ／band/positionBand（要確認）
Level 4宣言対象外・常に導出
positionCode userId groupEmployeeId employeeNumber ／costCenter/businessUnit等の組織階層コード ／payGrade（要確認）
Level 5宣言対象外・常に現状維持
各種フラグ・memo・promotionSign等の管理用メタ情報

⚠ MUST_CONFIRM_FIELDS — Levelに関わらず必ず確認Bへ

band / positionBand / payGrade — 報酬に直結する

employmentType — 他フィールドの許容値の土台になり、誤ると既存バリデーションで発見できない

officialPositionCode — 昇降格マトリクスの起点。誤読すると昇格と横異動を取り違える

Level・確信度に関わらず固定で確認対象にする、事前定義済みのリスト。

// Output: DocumentScope
{ sourceId: string, declaredLevel: 1|2|3 }
検証方法：UIの選択のみ。ロジック側は「宣言Levelを超えるfieldKeyのFieldStateを生成しない」という単純な分岐。
準備2

スライド分解

新規・機械的

PPT数十枚を1枚＝1画像に分解する。LLMは使わない。以降すべての処理の基本単位（抽出・実行）をこの「1枚」に揃える。

抽出1

Vision観測抽出

新規

1枚＝1呼び出しで並列にファンアウト。DocumentScope.declaredLevel以下のフィールドだけを対象に、正規化・コード化は一切せず生テキスト＋確信度＋根拠だけを出す。 上司関係は同一画像内の別の観測人物への参照として、位置関係から抽出する（まだ実在のmanagerPositionCodeではない）。 構造的な差分では読み取れない「休職・退職・移籍」等の明示的な注記は、proceduralNoteとして別枠で拾う——これはフィールドの変化ではなく宣言そのものなので、他のフィールドと同じ扱いにしない。 

// Output: PersonObservation[]
{
  obsId: string, slideIndex: number,
  name: FieldState<string>,
  org?: FieldState<string>, title?: FieldState<string>,
  employmentStatus?: FieldState<string>,

複数人が参照する同一の生テキストをグルーピングし、UnresolvedFactに束ねる。「この組織名は12人分で共有されている」という逆引きが、そのまま確認Aの優先度になる。

抽出3

確認A — 共有される曖昧さの確認

対話あり

linkedFieldStates.lengthの多い順にソートし、上位数件だけを最初に見せ、残りは任意で展開する。自分のペースで片付けられる一覧にする。 回答すると、参照している全FieldStateがconfirmedへ遷移する。

検証方法：ユニットテストではなく実利用での反復調整が前提。
判定1

名寄せ

新規・未設計

抽出した人物を既存allocationListの行と照合する。誤ると別人の行を書き換えるという、パイプライン全体で最も重い事故につながるため、他のどの段階よりも慎重な設計が必要。 上司として参照された人物（managerRef）も同様に名寄せが必要。 同一のmatchedRowIdに複数のobsIdが一致することを許容する——同じ人物が画像内の2箇所（本務先と兼務先）に登場するケースの検知に必要（判定-4で兼務系操作の判定材料になる）。 

// Output: IdentityResolution[]
{ obsId: string, matchedRowId?: number,
  candidates?: { rowId, score, matchedOn: string[] }[],
  status: 'matched'|'ambiguous'|'new_person'|'unresolved' }
// 同じ matchedRowId を持つ IdentityResolution が2件以上あれば「複数観測」——判定-4が使う
検証方法：純粋関数。(観測, 候補行群) → 一致/複数候補/新規、という入出力でユニットテスト可能。現時点で未設計。次に着手すべき最優先項目。
判定2

マスタ正規化

新規＋既存流用

確認Aでconfirmedにならなかった、単独で確信度が高いFieldStateをFIELD_CONSTRAINTSのマスタへ解決しauto_resolvedにする。条件付き制約フィールドはここでは触らない。

検証方法：純粋関数。既存のFIELD_CONSTRAINTSのテスト資産と同じ流儀。
判定3

変更検知（no-opゲート）

新規

現在値とprevXxxの両方に対して、解決済みFieldStateを突き合わせる。一致していれば「変更なし」として判定-4（操作選定）に進まない。宣言外のフィールドは比較対象にならず素通りする。 proceduralNoteの有無・同一行への複数観測の有無も、フィールド差分とは別の「変化あり」シグナルとして持ち回る（判定-4の層1・層2が使う）。

// Output: ChangeSignal
{ rowId: number, hasChange: boolean, changedFields: string[],
  hasProceduralNote: boolean,       // 明示的な注記（休職等）の有無
  observationCount: number }        // 同一rowIdへの観測件数（2以上なら複数観測）
検証方法：純粋関数。(現在行, prevXxx, FieldState[]) → ChangeSignal、で機械的にテストできる。
判定4

操作選定

新規・未設計

1人（または1グループ）につき、単一の操作を選ぶのではなく、コマンドの「スタック」を組み立てる。ルールは4層に分かれ、層ごとに「排他（当たったら独占）」か「加算（複数同時に成立してよい）」かが違う。

  • 層1・宣言（排他）：proceduralNote（休職・退職・移籍等の明示的な注記）があれば、フィールド差分は一切見ずに対応する操作へ直行し、他の層を止める
  • 層2・多重観測（部分排他）：同一matchedRowIdに2件以上の観測があれば、片方を本務、もう片方を兼務系操作（ConcurrentAdd等）として扱う。本務側に層4の変化が別途あっても共存可
  • 層3・構造複合（排他）：後任配置のような、既知の固定順序パターンに一致すれば、その複数行ぶんのコマンド列を採用し、他の層を止める
  • 層4・構造単純（加算）：changedFieldsに含まれる各フィールドのうち、独立した意味を持つもの（組織・バンド・雇用ステータス…）ごとにルールがあり、該当するもの全部がコマンドとしてスタックに積まれる。同一行・互いに素なフィールドなので可換——組織とバンドが同時に変わっていれば、OrgTransferとPromotionの2件がどちらの順でも安全に積まれる
// 内部構造: OperationRule[]
{ id: string, tier: 'declaration'|'multiObservation'|'composite'|'structural',
  exclusive: boolean,          // true=成立したら他ルールを止める（層1・3）
  appliesTo(ctx): boolean, isMultiRow: boolean,
  build(ctx): { operationId, rowId, values } | { multiRowDefId, sectionValues } }

// Output: ProposedChange[] — 1人・1グループぶんのスタックを、複数件のエントリで表す
{ stackId: string,             // 同じ人・同じグループに属するコマンドをまとめる単位
  order: number,               // スタック内の順序（層4同士は可換なので大小に意味を持たせなくてよい）
  kind: 'single'|'multiRow', operationId?, multiRowDefId?,
  rowId / rowIds, values / sectionValues,
  confidence: number, ruleId: string }

proceduralNote='休職' → LeaveOfAbsence単独。フィールド差分は見ない

各ルールは、実装コードの直前に決まった見出し構成のコメントを書く形で定義する。別のMarkdown定義書は作らない——コードと離れた場所にある仕様書はドリフトするため（今回のドキュメント整理でも痛感した）。 

/**
 * OperationRule: BandChanged
 * ─────────────────────────────────────────
 * 層: structural（層4・加算）　対象操作: Promotion / Demotion
 *
 * 信号: ChangeSignal.changedFields に band/positionBand を含む
 * 判定根拠: masters.jobLevels の promotionDemotionWarningLevel で比較
 * values構築: positionBand=判定-2の解決値／バンド上昇なら transferReason を分掌異動で確定
 * 検証（同値クラス）: ①上昇→成立(Promotion) ②下降→成立(Demotion) ③未観測/不変→不成立
 */

/**
 * OperationRule: SuccessorSwap
 * ─────────────────────────────────────────
 * 層: composite（層3・排他）　対象操作: vacatePosition + assignPersonToVacant + (必要なら)ManagerChange
 *
 * 信号: ①Aのポジションが観測されなくなった ②BがAの元positionCodeに新規観測される
 * 固定手順: 1.vacatePosition(A) 2.assignPersonToVacant(B, 手順1の空席) 3.他の部下のmanagerPositionCodeを個別更新
 * 未解決になるケース: Aの行き先が不明 → 成立させず確認Bへ
 * 検証（同値クラス）: ①両方確認できる→成立 ②行き先不明→不成立 ③Bが既存いずれとも不一致→対象外
 */

集約は既存のALL_EDIT_OPERATIONSと同じ発想で、ALL_OPERATION_RULESという配列にまとめる（新しいルールが見つかるたびに育てていく）。判定-4は排他層（層1→層2→層3）を順に見て、成立すればそこで確定、どれも成立しなければ層4に該当するもの全部を集める、という走査をするだけ。

🔒 層4の可換性は前提ではなく、テストで保証する

「層4は互いに素なフィールドしか触らないから可換」というのは、新しいルールを足すたびに機械的に検証する——各ルールの対象操作が実際に書き込むフィールドを把握し、層4のどの2ルールも書き込み先が重ならないことをテストで確認する。重なりが検出されたら、それは層4に置いてはいけないサイン——層3へ個別の固定順序ルールとして持ち上げる。非可換な組み合わせへの一般的な自動解決は、意図的に持たせない（層3で人が個別に順序を決める、という前々回の結論のまま）。

検証方法：純粋関数。既存のtests/helpers/operationRunner.tsと同じ流儀でシナリオテストできる。層4は各ルールを個別にテストできる。層3（複数行）のルールが現時点で薄く、拡充が本体作業になる。
判定5

ドライラン検証

新規・薄い

ProposedChangeをコミットせずに検証する。使うのは既存のvalidate()/apply()そのもの——executeOperationを呼ばず、結果を破棄するだけ。 同じstackIdのエントリはorder順に連続してドライラン（層4同士は可換なので実質どの順でも良いが、層3の複合スタックは決め打ちの順で1回通す）。

  • validate()が失敗 → 「検証エラー」として確認Bへ強制的に上がる（黙って落とさない）
  • validate()は通るが、導出後の最終値が元のFieldStateの観測と食い違う → 同様に確認Bへ

「自己修復」（AIが自動で値を調整して再試行する）は採用しない。原則7と矛盾するため。executeBatchが最初の失敗コマンドで全体を中断する仕様（後述のバグ2）を踏まえると、ここで事前に弾いておくのは実質必須の前段になる。

検証方法：既存のvalidate()/apply()をそのまま呼ぶだけなので、新規テストはごく薄い。
判定6

確認B — 提案そのものの確認

対話あり

ProposedChangeのうち、①confidenceが閾値未満、②複数のOperationRuleが競合、③ドライランで検証エラー・食い違いを検出、④MUST_CONFIRM_FIELDSに触れる——のいずれかに該当するものを見せる。同じstackIdのエントリはまとめて1件として提示する（スタック全体を人に見せる）。 対象は「変更のある人」だけ（判定-3で絞り込み済み）。対応しなかった項目は既存のレビュー画面にそのまま残る。

適用1

実行・Undo

既存のまま・無改変

確認Bを終えたProposedChangeをbindOperation(op, rowId, values)にかけ、executeOperation() / executeBatch()へそのまま渡す。1スライド＝1バッチ＝1Undo単位。 新しいコードは足さない。validate()・apply()・A〜G/W系バリデーション・UndoStackはこれまで通り。

検証方法：新規テスト不要。既存の実行パスのテストでカバー済み。
適用2

反映結果の提示

既存を流用

実行後、何が反映されたかを見せるだけの、アクション不要な軽い一覧。新しいロジックは作らず、既存のEditPatternバッジ・レビュー画面をそのまま使う（人が普通のExcelインポート後に確認するのと同じ画面）。 おかしいと気づいた場合の対処も、パイプラインの自動リトライは作らず、普通の手動編集・Undoに委ねる——ここでループは作らない。

既存コードの修正点（総まとめ）

このパイプラインを設計する過程で見つかった、既存コードの実際の不具合・ドキュメントとの乖離。上のOpen Itemsと内容が重複するが、見落とし防止のためここに集約する。 いずれもこのパイプラインの設計そのものとは独立した、既存コードの問題であり、今回のドキュメント作成中にコードへの変更は行っていない。

BUG 1

ロック排他制御が実行時に効いていない

apps/web/src/application/HRApplicationService.ts — executeOperation() / executeBatch()
問題

operationRole（lock/softLock）の排他制御はresolveAvailability()（packages/domain/src/commands/defs/index.ts）にしか実装されておらず、実行系のexecuteOperation/executeBatch自体はこれを呼んでいない。

影響

人はUIメニュー経由で必ず1操作ずつ実行するため今まで顕在化しなかった。プログラムから複数コマンドを直接executeBatchに積む経路（本パイプライン含む）では、本来矛盾するはずの操作（例：退職ロック中の昇格）が両方成立してしまう。

修正の方向性

executeBatchのループ内で、各コマンド適用前にその時点のチェーン済み行状態に対してresolveAvailability()相当のチェックを通す。

BUG 2

executeBatchが全体を巻き込んで中断する

apps/web/src/application/HRApplicationService.ts — executeBatch()（if (!vr.ok) return vr）
問題

ループ内で1つでもvalidate()が失敗すると、その時点でバッチ全体を中断する（all-or-nothing）。

影響

1スライド分（数十人）を1バッチにまとめて実行する設計だと、1人のエラーで全員分の反映が止まる。本パイプラインでは判定-5（ドライラン）で事前に弾くことで実質的に回避しているが、executeBatch自体の性質としては残ったまま。

修正の方向性

今回は回避策（ドライラン）で対応。executeBatch自体を部分成功対応にするかは、他の利用箇所への影響も含めて別途判断が必要。

BUG 3

ドキュメントが存在しないメソッドを記載している

apps/web/CLAUDE.md — 「操作の呼び出し方（UIから）」セクション
問題

appService.executeScenario({ label, commands })という記載があるが、実装はexecuteBatch(label: string, commands: EditCommand[])という別シグネチャ（位置引数）。EditScenarioという型自体、メインツリーのソースコードに存在しない。
