PersonnelAllocation ／ AI チャット

AIチャットの構成と改善の手引き

AIチャットは業務ツールで、LLM の応答が遅いぶん、そのまま操作の待ち時間になる。 だから設計の主眼は、少ない往復で安全に答えへたどり着くこと ── LLM の周りに ルール（プロンプト）・道具（ツール）・安全な経路（Operation モデル） を用意する。 この足場を ハーネス と呼ぶ。応答の速さも答えの正しさも、このハーネスの質で決まる。 この文書は、そのハーネスをほどいて改善の勘所を示す。

対象読者 AIチャットをチューニング・改修する開発者 前提 specs/G4-ai/ ・ docs/08,16 を既読 実装 apps/web/src/infrastructure/ai/ ／ application/aiTools/

01何を作るか

AIチャットは、ユーザーの言葉を受け取って、UI と同じ操作の仕組み（Operation モデル）を動かす。 UI との役割分担ははっきりしている ── UI は「確実で速いこと」、AI は「言葉にしないと伝わらないこと」を受け持つ。

受け持つこと
UI自分の部門の表示、入力できる項目の制限、その場のエラー表示、画面で選んだ行のまとめ操作
AIあいまいな指示、ルールの説明、条件を指定したまとめ処理、探す・下書きするといった手間の代行

できることは4つ

この4つには順番がある。1（探して、見せる）で対象を特定してからでないと、教える・手伝う・変更するはできない。 2〜4 は 1 のあとに続く。

  1. 1 探して、見せる 名前や組織から対象の行を見つける。必要なら組織ツリーや一覧をチャットの中に表示する 何も変えない
  2. 2 教える 「この項目に何を書くか」「選べる値は」「なぜエラーか」を、ルールに沿って説明する 何も変えない
  3. 3 画面を動かす・下書きする 対象を組織図で表示する、表示を切り替える、操作フォームを開いて値を下書きする（送信はユーザー） 画面だけ動かす
  4. 4 変更する 実際にデータを書き換える。AI が対象と値を用意し、確認用のプレビューを出し、ユーザーが承認してから実行する データを変える・確認を挟む
3 と 4 に共通する形

面倒な部分 ── 対象を探す、値を計算する ── は AI が代行し、最終確認はユーザーがする。 結果や確認内容は、チャットの中に小さな UI（組織ツリー、確認フォーム、差分プレビュー）として出る。これを ウィジェット と呼ぶ。

対応するツールの種類 ── ① read / render、② read（getFieldOptions ほか）、③ navigate（ui_*）、④ execute / confirm。 チャット内のウィジェットは render と confirm の戻り値。

組み合わせでできること

上の4つを順番に組み合わせると、大きな作業になる。新しい「機能」に見えるものも、たいていはこの組み合わせで、専用のツールは足していない（スキルか固定手順のプロンプトで表す）。

  • エラーの解消 ── 探す①→ 理由を教える②→ 直す④
  • 体制図どおりに一括編集 ── 指示文を読み取り、①→④ を繰り返す（概要確認／要確認のレビュー／一括実行、の3段階）
  • 玉突き人事 ── ①→④ を、順番を守って実行する

02考え方 — LLM にルールと道具を与える

これは業務ツールである

人事異動の記入は締め切りのある実務で、ユーザーは作業を早く終わらせたくてチャットを使う。 LLM は1往復ごとに数秒かかり、それがそのまま操作の待ち時間になる。 だから設計の主眼は、1回のやり取りでできるだけ処理を進め、少ない往復で答えにたどり着くこと。

もう一つ。この業務は、担当者が未知の状況を推論して値を決めるのではなく、決まったルールに沿って記入する作業がほとんど。 AI に期待するのは「言いたいことを汲み取って、正しい操作に振り分ける」こと。 往復を減らす設計にしても、答えの質は落ちない。

帰結 ── LLM に足りないものをハーネスで補う

LLM 単体は、この業務のルールを知らないし、データを安全に書き換える手段も持たない。 そこを埋めるのがハーネス ── LLM を「仕事ができる状態」にするための足場。LLM の周りに3つのものを用意する。

  • ルール ── 業務知識・禁止事項・手順をシステムプロンプトで渡す
  • 道具 ── 事前に定義した安全な操作をツールとして渡す（生のデータ書き換えはさせない）
  • 安全な経路 ── 不可逆な操作は確認を挟み、ループの往復を最小に保つ（オーケストレーター）

Anthropic は「効果的なエージェントは複雑なものではなく、良いツールを備えた単純なループ。知能はモデルの能力・ツール記述の質・タスクの枠組みから来る」と言う[1]。 モデルの能力に賭けられない分、後ろの2つ ── ツール記述の質とタスクの枠組み ── をしっかり作る。 1つのツールが1つの業務操作をまるごと担い、必要な文脈は最初にまとめて渡す。

この文書の主題

LLM を囲むもの ── システムプロンプト・ツール・オーケストレーション・Operation モデル ── をまとめて ハーネス と呼ぶ。 答えの速さも正しさも、このハーネスの質で決まる。 モデルを新しくするのを待つ話ではない。以降は、そのハーネスをほどいて着手点を示す。

外部の位置づけ

「ハーネス」はこのプロジェクトの呼び方だが、中身は広く知られた枠組みそのもの。

  • OpenAI ── 「エージェント ＝ Model ＋ Tools ＋ Instructions、加えて Guardrails と Orchestration」[4]
  • Anthropic ── 「augmented LLM ＝ model ＋ retrieval ＋ tools ＋ memory」[1]（本システムは retrieval と memory を持たない ── §9 で扱う）

次章の「3つの接点」は、この Instructions ／ Tools ／（Guardrails＋Orchestration）を LLM の周りに並べ直したもの。

03三つの接点

§2 の3つ ── ルール（指示）、道具（ツール）、安全な経路（制御） ── が、LLM に触れる3つの接点になる。 改善の手を入れられるのも、突きつめればこの3か所しかない。まず全体図で位置関係を掴む。

図の読み方（①→②→③）

  1. ① 指示 ── 人がチャット欄に入力した内容は、LLM が知らない業務ルール・手順・禁止事項（システムプロンプト8層）と一緒に LLM へ渡る。
  2. ② 行動範囲 ── LLM はツールを呼んで動く。ツールは目的で4系統に分かれ、行き先が違う ── 参照系はドメインのデータを直接読み（getSnapshot()）、 Web UI 系は画面 UI を操作し、 ドメイン操作系は Operation モデルを通じてデータを変え、 スキル読込系は手順本文を LLM に返す。 AI 内で完結するときはウィジェットが人との接点（表示・承認・入力）。
  3. ③ 制御 ── オーケストレーターがこのループを回す。変更操作は確認ゲート（ウィジェット、または画面 UI で人が承認・送信）を通り、 Operation 収束（validate → Undo → apply → emit）を経て、結果が両領域に反映される。 AI ↔ 画面 UI の受け渡しは uiCommandStore（AI → 画面）と formStateStore（画面 ⇄ AI）が担う。

① 指示 ── システムプロンプト≈ Instructions / Context Engineering

  • 役割 ── LLM が知らないこと（業務ルール・ツールの使い分け・禁止事項・固定手順）を毎ターン注入する。
  • 構造 ── 8層。固定核（BASE_SYSTEM_PROMPT 約90行）＋ 動的文脈 ＋ 学習ルール ＋ スキルヒント ＋ パス別末尾。
  • 要点 ── buildCurrentSystemPrompt が毎ターン組み立て直す。「1回書くプロンプト」ではなく「毎回 curate する文脈」。3000行のデータは入れず、件数だけ入れて詳細はツールで取らせる ── 大きな文脈はモデルの注意を薄める[2]。
8 層（上から順に積む）

どこに何を書くか ── ツール1個の意味は description に。ツールの使い分けはプロンプトに（description だけでは LLM が選びきれない）。いま何件・どの組織といった状況は動的層に。スキルの手順は SKILL.md に。

② 行動範囲 ── ツールとスキル≈ Tools

ツールは LLM が世界に触る唯一の方法。1ツール＝1能力。分類には2つの軸がある。

  • 目的で4系統 ── ツールを「何のために呼ぶか」で分ける。改修時にどのファイルを触るかがこれで決まる。
  • 副作用で5種別（kind） ── 「実行して安全か」で分ける。オーケストレーターはこの kind で処理を振り分ける。
目的による4系統 × 副作用による kind

kind の意味 ── read＝見る（副作用なし）／render＝見せる（ウィジェット）／navigate＝画面を動かす（UI 状態のみ）／execute＝即時にデータを変える／confirm＝確認してからデータを変える。全リストは §8。

  • 2層構造 ── プロトコル層（toolRegistry：名前・引数スキーマ・種別）／実装層（aiTools：実ロジック ＝ AI BFF）。toolRegistry でドメイン操作を直接書かない[3]。
  • 露出制御（progressive disclosure） ── Fast Path は参照系＋Web UI 系のみ（getSafeDefinitions）／スキル起動後は allowed-tools に列挙されたものだけ。
  • スキル ── 決まった順序があるタスクの手順書（SKILL.md）。該当時だけ LLM に渡り、呼ぶと手順本文が返り、以降ツールが絞られる。現在4つ ── cascading-transfer ／ mark-absence ／ promotion-workflow ／ query-validation。

③ 制御枠 ── オーケストレーターと Operation 収束≈ Orchestration + Guardrails

  • オーケストレーター（agentRunner ＋ useChatHandlers）── ループの管理、Fast / Structured の切替、確認の割り込み、毎ターンのログ記録。
  • Operation 収束 ── aiTools.executeXxx() → service.executeOperation(new XxxOperation()) → executeScenario → validate → UndoStack → apply → emit。AI が不正な値を直接書けない。
  • 確認ゲート ── buildProposal（DryRun）→ onConfirm（ループ停止・ユーザー待ち）→ executeOnApprove。
  • バリデーションはドメイン層で UI と共有 ── ツールを強化すれば AI も同じ制約で動く正のループ。

04エージェントループ

ユーザーが1回何か言うと、処理は一直線には進まない。 LLM がツールを呼ぶ → 結果を見てまた呼ぶ、を必要なだけ繰り返し（ReAct と呼ばれるやり方[5]）、 次の3つのいずれかでそのターンが終わる。

  • 答えを返して終わり ── 検索・説明の結果を、文章かウィジェットで返す
  • Web UI に渡して終わり ── フォームを開く・下書きする。あとは人が画面で進める（AI のターンはここで終了）
  • 確認ゲートを通して書き込む ── 変更操作。重い経路（Structured Path）と、チャット内の承認を経て Operation モデルへ

軽い経路（Fast Path）でできるのは最初の2つ。3つ目だけが重い経路に切り替わる。

  • Fast Path ── 露出するのは安全ツールだけ（getSafeDefinitions()）。各ターン最大10往復（MAX_ROUNDS）。
  • エスカレーション ── LLM が「変更・複数手順が必要」と判断したら request_structured_planning を呼ぶ。実行はされず、ActionFrame を返してオーケストレーターが Structured Path を起動する。missingInformation / suspectedOperation は現状未使用
  • Structured Path ── 全ツール＋スキル。スキルを呼ぶと手順本文が返り、以降 allowed-tools でツールが絞られる。
  • 履歴の扱い ── 次ターンへ渡す履歴から tool 呼び出しと結果が除かれ、最終テキストだけが残る。複数ターンの作業では文脈が薄れる（§7）。
外部の位置づけ

「Fast / Structured の2段」は Anthropic の「まず最も単純な解、必要なときだけ複雑さを足す」[1] の一実装。前段に意図分類器を置いて guide / simple / wizard に精密ルーティングする案（Tier）は 未実装 ── 構造化出力の対応確認待ち。

05七つの判断（分析軸）

これは一般的な用語ではなく、この仕組みを調整するために独自に切り分けたもの。 ループのどこで、誰が（コードか LLM か）、何をもとに決めているかを並べる。 コードが決める ものは確実に直せる。LLM が決める ものはプロンプトとツール定義で誘導するしかない ── この違いが改修の難しさを決める。

#判断主導根拠にする情報設定・改修箇所外すとどうなる
1Fast か Structured か コード FAST_PATH_SUFFIX ／ 擬似ツール description fastPathTool.ts 変更なのに read で終了／軽い照会が重パスへ
2どのツールを呼ぶか LLM ツール description ＋ プロンプトのルーティング規則 ＋ 露出ツール集合 chatSession.ts ／ *Tools.ts ／ getSafeDefinitions 似たツールの取り違え
3どんな引数で LLM ツール parameters ＋ 動的層（ピン留め行の rowId 等） パラメータ定義 ／ プロンプト動的層 rowId 取り違え・必須欠落
4どのスキルを起動するか コード SKILL.md の description（＝トリガー文） SKILL.md frontmatter スキル不発火・無関係スキル起動
5結果をどう解釈し次に何をするか LLM tool メッセージ（JSON）＋ プロンプトの後処理ルール（例：操作後は必ず getValidationDiagnosis） プロンプト業務ルール節 診断せず完了報告・堂々巡り

7最終回答に何を書くか LLM 会話履歴（tool 呼出は除去済）＋ 表現ルール（内部フィールド名を見せない等） プロンプト 内部語の漏れ・要約不足

判断 1・4・6 はコードが決める（＝ハーネス側で確実に直せる）。2・3・5・7 は LLM が決める（＝プロンプトとツール定義で誘導するしかない）。 OpenAI の言う「入力の検査からツールの利用、人による承認まで、すべての段階で歯止めをかける」[4] を、判断ごとに割り当てたもの。

07これから

学習ループ（Teach AI）── 今回は非リリース

発想 ── HR 専門家の訂正そのものが業務ルールの根拠（統計的確信度は不要）。 AI を使いながら「これは違う」「こういう場合はこうする」と訂正していく行為が、そのままルール構築のプロセスになる。

仕組み ── 訂正 → LLM 1回で5分類（ツール説明ミス／ルール欠如／手順欠如／ロジックバグ／ツール不足）。 上3種は localStorage で即日適用（ツール説明の上書き・学習ルールのプロンプト注入・スキル生成）、下2種は Claude Code 向けタスクとして蓄積。

なぜ筋が良さそうか

既存資産（applyDescriptionOverrides ／ スキル機構 ／ プロンプト注入層 ＝ §3 の3接点そのもの）にそのまま乗る ── 追加実装が小さい。 毎ターンの runLog と feedbackLabel が精度計測の下地になっている。 STEP2（不特定多数）では「1人の訂正を即ルール化」は危険なので、複数人シグナルの統計集約に発展させる道筋も設計済み（構想のみ）。

8.1 システムプロンプトの原文

第1層：BASE_SYSTEM_PROMPT（chatSession.ts。文字列連結を展開したもの）

あなたは人事異動管理システムのAIアシスタントです。組織異動・出向・兼務追加・昇降格など、人事異動に関する操作をサポートします。要員配置リストのデータに基づいて、簡潔・丁寧に回答してください。

## ツール利用ガイドライン
- ピン留め行（システムプロンプトの「ピン留め参照情報」セクション）の userId・rowId・orgCode はすでに提供済みのため、findPersons/getPersonsDetail を呼ばずに直接使ってよい。
- ピン留めされていない従業員を探すときは findPersons を使う。名前が曖昧な場合は候補を列挙してユーザーに確認する。
- 役職変更（「課長にして」等）は propose_change_position を使う。propose_field_edit は補足情報の編集のみ。
- 組織コードが必要なときは findOrgs で取得する。
- propose_* (confirm 系ツール) は name / subtreeOrgCode / rowId 等のフィルタパラメータを自身で持つ。対象を特定する目的だけで findPersons/findOrgs を先に呼ぶ必要はない。
- confirm ツール（propose_*）は必ずユーザーの確認を得てから executeOnApprove が呼ばれる。承認前に「実行した」と言わない。
- 「変更を教えて」「変更の概要は？」→ getReviewSummary でサマリーを取得してから回答する（件数が多くても安全）。詳細一覧が必要なら getChangedRows を続けて呼ぶ（limit/offset でページ案内、truncated で続きの有無を確認）。
- 「組織図を見せて」「全体像を見せて」には getOrgTree を使う。
- フィールドに設定できる値を確認するときは getFieldOptions を使う。
- スコープ（作業対象組織）が設定されている場合、操作対象はそのスコープ内に限定される。
- 操作完了後は必ず getValidationDiagnosis を呼んで問題を確認し、自動修正可能なものから提案する。
- getValidationIssues / getValidationDiagnosis の結果にある `field`（camelCase の変数名）はユーザーに見せない。代わりに `fieldLabel`（日本語ラベル）を使って説明する。

## UIナビゲーションツール（データ変更なし・Fast Pathで使用可）
- 「〇〇さんを見せて」「〇〇さんの場所を教えて」→ ui_show_person（名前で検索してキャンバス上にフォーカス。findPersons + 画面移動を1ステップで行う）。
- rowId が既に分かっている場合は ui_focus_row で直接フォーカスできる。
- 「〇〇さんの昇格フォームを開いて」「異動の画面を出して」→ ui_open_operation（操作フォームを開き、prefill で値を事前入力する）。
  findPersons で rowId を確認し、getFieldOptions で有効な選択肢を確認してから呼ぶこと。
  フォームはユーザーが確認・送信する（AIは送信しない）。
- 「今フォームに何を入れればいい？」「選択肢を教えて」→ ui_get_form_state を呼ぶ。
  Promotion/Demotion フォームの場合は bandRecommendations（UIのデフォルト推奨バンド）が付いてくる。
  positionBand に何を設定すべきか聞かれたときは必ず ui_get_form_state を呼んで bandRecommendations.oneStep を確認する。
- フォームの特定フィールドを設定したい場合 → ui_suggest_form_field（onFieldChange の連動導出も正しく走る）。

## 業務ルール
- 昇格は propose_promotion に rowId と newPositionBand を渡すだけでよい。band / payGrade は自動導出され確認UIに表示される（DryRun）。
- payGrade（給与等級）が変わる場合は必ず新しいポジションを作成する。バンドが変わらなくても jobType 変更で payGrade が変わる場合も対象。
- 部下を持つ人（ピープルマネージャー）が異動してもポジションはクローズしない。後任者が同じポジションを引き継ぐことで部下の managerPositionCode 更新を防ぐ。
- positionCode が "_pos_" で始まる場合は内部採番コード。Excel 出力時は空欄になる。
- prevXxx フィールド（発令前の状態）は変更しない。
- managerPositionCode を変更するときは propose_set_manager_position を使う（saveRow で直接変更すると managerName が更新されない）。
- 兼務を示す申請区分（transferReason）が選択されている場合、leaveOfAbsenceSign は設定できない（バリデーションで検出される）。

## 出向操作
### SF統合先 / SF外の区別
- SF統合先: 自社と同一 SuccessFactors に統合されている会社。masters.companies[].isSFIntegrated = true で判定。
- SF外: SF に統合されていない会社（グループ内でも別システム）。レコードを手動管理する必要がある。
### 出向させる（自社 → 他社）
- 本務出向（SF統合先）: ui_open_operation operationId="SecondmentOutSF"（1行操作）
- 本務出向（SF外）: ui_open_operation operationId="NonSFSecondmentOut"（出向箱更新＋受入行新規の2行セット）
  → SF外の場合、出向元担当が受入側レコードも代理作成する。フォームに従って2行を同時確認する。
- 兼務出向（SF外のみ）: ui_open_operation operationId="ConcurrentSecondmentOutNonSF"
- 兼務出向（SF統合先）: SF側が管理するため本ツール操作不要。
### 受け入れる（他社 → 自社）
- 本務出向受入: ui_open_operation operationId="SecondmentInReleaseSF"（SF統合先）または "SecondmentInReleaseNonSF"（SF外）
- 兼務出向受入: 組織パネルの追加ボタンから操作（AI直接操作不可）
### 解除・取消
- 本務出向解除（SF統合先帰任）: ui_open_operation operationId="SecondmentOutReleaseSF"
- 本務出向解除（SF外帰任）: ui_open_operation operationId="NonSFSecondmentRelease"（出向箱更新＋受入行削除の2行セット）
- 「出向先に転籍させたい」→ propose_secondment_transfer（出向解除→転籍の2ステップを1操作で提案）
### 出向箱
- 本務出向時、出向元の行は「出向箱」(concurrentType="出向箱") として残る。SF上では席として存在するが発令先は出向先。
- 出向箱行を findPersons で検索すると concurrentType="出向箱" で識別できる。

## 4/1 不在（退職・移籍）操作
- 「退職させて」「移籍させて」「4/1 不在に登録して」→ propose_mark_absent を使う
  - absenceType="退職": 3月末退職・解任済みとして登録（transferReason 自動設定）
  - absenceType="移籍": 4/1付移籍として登録（transferReason 自動設定）
- 不在登録後、部下がいる場合は W系警告「退職予定者の部下が存在する」が出る
  → getValidationDiagnosis で確認し、部下の上司を propose_set_manager_position で変更するよう提案する
- 「不在を取り消して」「誤登録を戻して」→ undo または propose_field_edit で transferReason をクリアする

## 分断された上司ポジション（別ファイルの上司）
- Excel が組織単位に分割配布された場合、上司行が別ファイルにあるため managerPositionCode が解決できないことがある
- バリデーション警告「上司ポジションコードがこのファイルに存在しません（別組織の可能性あり）」はこの状況を示す
  → **この警告は自動修正しない**。マージ後に解決されるため、クリアや変更を行わないこと
- ユーザーから「↑ 別組織 と表示されているのは何？」と聞かれたら:
  「上司が別のファイル（別組織の担当者が管理している Excel）にいるため、現時点では表示できない状態です。
   全ファイルのマージ後に正しい階層で表示されます」と説明する
- `(上司不明⚠)` と表示されている場合（全ファイルにも上司行がない）は、
  上司が廃止・削除された可能性がある。propose_set_manager_position で別の上司に変更するよう提案する

## 禁止事項
- prevXxx フィールドを直接変更すること
- positionCode を "_pos_" prefix なしで自己採番すること
- managerPositionCode を propose_set_manager_position 以外の方法で変更すること
- 「上司ポジションコードがこのファイルに存在しません」警告を自動修正すること

## 体制図インポートフロー
「以下の体制図変更指示を処理してください」や「## 異動」「## 昇格」等の見出しを含む変更指示テキストを受け取ったとき、以下の3フェーズで処理する。

Phase 1 — サマリー確認:
  変更種別ごとの件数をまとめ、確定できるものと要確認のものを分けて提示する。
  ユーザーが「合っている」と確認してから次へ進む。不一致があれば差異を特定して確認する。

Phase 2 — 要確認項目レビュー（バンド未確定の昇格→❓要確認 の順）:
  - getFieldOptions でバンド・役職の選択肢を取得してユーザーに提示する
  - 役職名から典型バンドを推測してよいが「推測です」と明示する
  - ユーザーが「わからない」「スキップ」→ propose_field_edit で memo に「要確認: {内容}」を記入して次へ進む
  - 全件確認が終わったら Phase 3 に進む

Phase 3 — 一括実行:
  - 同じ行先への異動は propose_bulk_transfer でまとめる
  - 全実行後に getReviewSummary で変更件数を確認してユーザーに報告する

## 実行モード: Fast Path

現在は以下の操作が実行できます:
- **情報の読み取り・検索・表示**（findPersons, getReviewSummary, getFieldOptions 等）
- **UIナビゲーション**（ui_* プレフィックスのツール。画面フォーカス・フォームを開く・フォーム値を入力補助）

UIナビゲーションツールの用途:
- ui_show_person: 「〇〇さんを見せて」→ 画面上で人物にフォーカス（検索+表示を1ステップ）
- ui_focus_row: rowId が既知のときにキャンバス上でフォーカス
- ui_open_operation: 「昇格フォームを開いて」→ 操作フォームを開いて値を事前入力
- ui_get_form_state: 現在開いているフォームの入力状態を読む
- ui_suggest_form_field: 開いているフォームのフィールドに値を設定

以下の場合は必ず request_structured_planning を呼んでください:
- 従業員・組織の情報を変更・更新・削除する（異動・昇格・兼務・出向・休職 等）
- 複数の手順を順番に実行する必要がある
- 意図が曖昧で確認が必要

情報の参照・検索・表示・UIナビゲーションだけで答えられる場合は、そのままツールを使って回答してください。

09抜本案：状態を持つハーネス

いまの設計は毎ターン完全にステートレス（§4）。1万行のリストも3千件の組織もプロンプトに載せられないので、 AI は必要な情報をそのつどツールで探す。しかも次ターンには結果が履歴から消える。 ここを変えると構成そのものが変わる ── そして、その変え方には 名前の付いた定石 がある。

いまの非効率

  • 1ターン内の三角測量 ── 「田中さん」→ findPersons → 複数ヒット → getPersonsDetail → getValidationIssues …と何度も往復して対象と文脈を組み立てる。
  • ターンをまたいだ再取得 ── 前ターンで調べたことをもう一度調べる（体制図一括編集・玉突き人事で顕著）。
  • entity resolution が弱い ── LLM が検索語を組み立てて絞り込むため、同名・表記ゆれで rowId を取り違える（判断3）。

これは既知の問題で、定石がある

「大きな構造データ ＋ ステートレスなエージェント」は広く議論されてきた。関連する枠組み：

枠組み要点この案での使いどころ
CoALA（Cognitive Architectures for Language Agents）[6] エージェントを「メモリ（ワーキングメモリ＝当面の文脈 ＋ 長期：意味／エピソード／手続き）」「行動空間（内部＝推論・検索／外部＝ツール）」「決定ループ」で整理する標準の参照枠。 新設する層＝CoALA の ワーキングメモリ。ドメインのデータは長期（意味）メモリにあたる。
LangGraph の永続化（checkpointer）[7] グラフの状態を各ステップ後にスナップショットし、同じ thread ID で再開すると前回の続きから走る。ターンをまたいだ状態を「作り直す」のではなく「持つ」。 「毎ターン履歴を捨てる」の直接の対策。まず打つ最小の一手。
Context Engineering：Write / Select / Compress / Isolate[8] 文脈の作り方を4種に分類 ── Write＝スクラッチパッドに書き出す／Select＝関連情報を検索で選ぶ／Compress＝要約して縮める／Isolate＝別エージェント・別ストアに分ける。 下の打ち手 A〜E がこの4分類にそのまま乗る（＝案が場当たりでない証拠）。
MemGPT ／ Letta（LLM as OS）[9] OS のページングに倣い、限られた文脈窓と外部ストレージの間でデータを出し入れして「大きなメモリがあるように見せる」。ただしメモリ管理を LLM 自身に任せる。 「10,000 行が載らない」への解答の骨格は採る。LLM に自己管理させる部分は採らない（下記）。

打ち手（Write / Select / Compress / Isolate に対応）

打ち手分類何をする効く非効率
Aツール結果ログの保持Write履歴から捨てず、圧縮した「これまで調べたこと」を毎ターン注入ターンまたぎの再取得
Bセッションダイジェスト層Compress件数・上位の問題・変更のあった組織・保留中の操作を常に最新で1ブロック注入getReviewSummary 等の往復

抜本案 ── CoALA のワーキングメモリ ＋ LangGraph の永続化

オーケストレーターと LLM の間に セッションコンテキストサービス（＝ CoALA のワーキングメモリ）を置く。

  • ワーキングセット ── いま扱っている行・組織の主要フィールド、解決済みの entity、手順とその進捗。HRApplicationService の snapshot から emit のたびに主要フィールドだけ作り直す（真実は1つ、これは派生キャッシュ）。
  • リトリーバル（Select）── entity 解決と近傍検索。3千組織・1万行なら素朴な索引で足りる（ブラウザ内）。
  • 注入（Compress）── 上限つきの「いま何を扱っているか」ブロックを毎ターン組む。
  • 永続化 ── この層を会話（thread）に紐づけて持つ（LangGraph の checkpointer に相当）。
MemGPT から採るもの／採らないもの

採る：階層メモリの発想（限られた文脈窓 ＋ 外部ストア、必要な分だけ載せる）。
採らない：メモリ管理を LLM 自身に任せる部分。この規模のモデル ＋ 人事データの安全性では、 何をワーキングセットに載せるかはハーネスが決める（snapshot から決定的に再構築）。LLM はその上で意図→操作をやるだけ。

これで LLM のツールが「探す」から「ワーキングセットを操作する」に縮む。 ステートレス LLM ＋ 再取得 → 状態を持つハーネス ＋ 薄い LLM。§2 のハーネスをもう一段厚くした形。

段階的に

  1. A（ログ保持） ── 履歴の圧縮ログ。1〜2日。すぐ効く。
  2. B（ダイジェスト） ── 第2層の拡張。1〜2日。
  3. C（リゾルバ） ── resolvePerson／resolveOrg ツール＋UI 曖昧性解消。1週間程度。
  4. D（ワーキングセット＋プラン） ── 新しい状態層。数週間。ここから「抜本」。
  5. E（サブエージェント） ── 体制図一括編集のみ先行導入。

リスク

  • 一貫性 ── ワーキングセットが snapshot とずれる。→ 派生に徹する（emit で作り直し、独自に書かない）。
  • 複雑性 ── 新しいステートフル層。テスト・デバッグの面が増える。→ D の前に評価ハーネス（§7）が必須。
  • セッション横断メモリは別問題 ── rowId はセッション内連番。localStorage に持ち越すと壊れる。ワーキングセットはセッション限定にする。
  • リトリーバル品質 ── 素朴な索引で足りなければ埋め込みが要る（モデル呼び出し or ローカルライブラリ）。まず決定的 fuzzy から。
