# 要件定義

## 背景と解くべき課題

人事部門・職場の担当者が毎回の発令作業（Excel → 確認・調整 → 人事システム反映）において、
「誰をどこに動かすと何が変わるか」を視覚的に把握しながら安全に編集できる仕組みがない。
本システムはその課題を解決するツールであり、**ブラウザ完結・バックエンドサーバー不要**で動作することで社内ネットワーク制約に非依存である（AI チャットを使う場合のみ `apps/server` のプロキシが必要）。

---

## スコープ

### In（このツールで完結）

- 発令案の作成・編集・Undo/Redo
- 組織図での発令前 / 発令後の可視化
- Excel インポート（発令前データ読み込み）
- Excel エクスポート（発令後データ出力 · 元ファイルの書式保持）
- AI アシスタントによる操作支援（Claude API 連携）
- 意味のある単位での操作（異動・昇格・出向・兼務 …）とバリデーション

### Out（スコープ外・将来拡張）

| 項目 | 理由 |
|---|---|
| 承認ワークフロー（稟議） | 別システムで担う |
| 権限管理・ロール | スタンドアロン運用を優先 |
| 給与・評価システム連携 | 別フェーズ |
| SuccessFactors API 直接読み書き | Phase 4〜5（[roadmap](./05-roadmap.md) 参照）|
| モバイル対応 | デスクトップ業務ツールとして位置付け |

## ユーザー（ペルソナ）

| ペルソナ | 主な使い方 |
|---|---|
| **取りまとめ担当**（HR担当者） | 全体ファイルを管理する。担当者割り当てウィザード、分割エクスポート、マージ、上司名補完、最終確認を行う。管理者モードで操作する |
| **組織担当**（部門担当者） | 自分が担当する組織の after 欄を記入する。担当者モードで操作する。新任者の追加も担当する |
| **システム管理者** | コードリスト（等級・職種・勤務地等）のマスタ更新を行う |

## データ設計の原則

**Single Source of Truth**: `HRApplicationService` が保持するコアデータだけが真の状態。その他（`persons`, `afterPositions` 等）はすべて**派生ビュー**であり毎回再計算される。

```
allocationList:      AllocationRow[]   ← prev*=発令前（不変）, after=発令後（編集可）
beforeOrganizations: Organization[]
afterOrganizations:  Organization[]
companies:           Company[]
codeLists:           AllCodeLists      ← LocalStorage にも保存
```

**Excel 後方互換・セッション永続化**: 操作の結果は常に `AllocationRow[]`（prev* + after 列構造）として保持されるため、どんな意味的操作を追加しても Excel エクスポート層は変わらない。コードリストのみ LocalStorage に保存し、発令案（allocationList）はメモリのみ保持する — Excel エクスポートが唯一の永続化であり、「うっかり中途状態が保存される」事故を防ぐ。

## バリデーション方針

純粋関数として単体テストできる3層構成。

| 層 | 責務 |
|---|---|
| **UI** | 入力ヒント・補助（placeholder、disabled 制御） |
| **`EditCommand.validate()`** | 操作の前提条件・業務ルール（純粋関数） |
| **`validateRow()`** | 行単位の整合性チェック（純粋関数） |

- [x] 1 人の担当者が扱う最大行数は？ → **約 3万行**（人もポジションも各 3万規模）。O(n²) 処理に注意

- [ ] 操作種別（異動・昇格・出向…）の具体的な業務ルール定義（特に FieldBinding の確定）
- [ ] AI によるポジション操作の対応範囲（自然言語で「空席を作って配属して」まで依頼できるか）
