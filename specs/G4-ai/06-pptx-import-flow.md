# G4-06: 体制図インポートフロー仕様

体制図PPTX/画像から人事変更指示を生成し、このアプリのAIエージェントで対話的にレビュー・実行する2段階フロー。

---

## 概要

```
[Stage 1] 外部ツール（LLM等）
  体制図PPTX/画像 → 変更指示テキスト（本ドキュメントの形式）

[Stage 2] このアプリのAIエージェント
  変更指示テキスト → サマリー確認 → 要確認項目レビュー → 一括実行
```

Stage 1 と Stage 2 のインターフェースは「変更指示テキスト」のみ。外部ツールとこのアプリは疎結合。

---

## Stage 1: 外部ツールへの要件

### 期待するアウトプット形式

```
## 異動（→ 行先部署名）
- 田中太郎（現: 営業本部）
- 鈴木花子（現: 営業本部）

## 異動（→ 経営企画部）
- 佐藤次郎（現: 総務部）

## 昇格
- 山田一郎（主任 → 課長）
- 中村健（課長 → 部長、バンド: M4）

## 降格
- 高橋誠（部長 → 課長）

## 役職変更（昇降格なし）
- 渡辺美咲（チームリーダー → スペシャリスト）

## 社内兼務追加
- 加藤拓也（本務: 開発部） ← 品質保証部

## 社内兼務解除
- 伊藤さくら（本務: 人事部）の品質保証部 兼務を解除

## 本務出向
- 松本隆（現: 経営企画部） → 株式会社○○ 営業部

## 兼務出向
- 木村智子（本務: 開発部） ← 株式会社△△ 技術部（兼務）

## 本務出向解除
- 吉田健二（株式会社○○ 出向中）→ 本務復帰

## 休職
- 小林美和

## 復職
- 森田誠

## 退職
- 西川一郎

❓ 要確認:
- 大野裕子（役職変更か異動か不明）
- 原田一郎（昇格と思われるがバンド不明）
```

### フォーマットルール

| ルール | 内容 |
|---|---|
| 変更種別の見出し | `##` で明示する。「→」だけでは異動か出向か判断できないため必須 |
| 異動のグループ化 | **同じ行先の人は1つの見出しにまとめる**（`propose_bulk_transfer` 最適化のため） |
| 人名 | フルネーム必須。同姓同名対策に現所属を `（現: 〇〇部）` で添える |
| 部署名 | 正式名称。略称は使わない |
| バンド | スライドに明記されている場合のみ記載。不明な場合は省略（アプリ側で確認する） |
| 要確認 | 操作種別が読み取れない・情報不足の場合は `❓ 要確認:` セクションに列挙 |
| ノイズ除去 | ロゴ・装飾・スライドタイトル・コメント等は除外する |

### 変更種別と EditPattern の対応

| 指示テキストの見出し | アプリ内 EditPattern | 備考 |
|---|---|---|
| 異動 | 社内異動（orgTransfer） | 行先部署ごとにグループ化 |
| 昇格 | 昇格（promotion） | バンド未確定の場合は Phase 2 で確認 |
| 降格 | 降格（demotion） | |

### Stage 1 プロンプト例（外部LLMに渡すプロンプト）

体制図のスライドテキストを外部LLM（Claude/GPT-4o等）に渡す際のプロンプト。

```
あなたは人事異動情報の構造化アシスタントです。
以下のスライドテキストを読み取り、人事異動の変更指示を指定の形式で出力してください。

【出力形式】

変更種別ごとにセクションを作り、該当者を列挙してください。
使用するセクション見出し（## ）は以下のいずれかのみ使用してください:
  異動（→ 行先部署名）、昇格、降格、役職変更（昇降格なし）、ジョブタイプ変更、雇用延長、
  社内兼務追加、社内兼務解除、
  本務出向、本務出向受入、本務出向解除、本務出向受入解除、
  兼務出向、兼務出向受入、兼務出向解除、兼務出向受入解除、
  休職、復職、移籍（出る）、移籍（入る）、退職

異動は行先部署ごとにグループ化し、
見出しを「## 異動（→ 行先部署名）」とすること。

各人物の記載形式:
- 氏名（現: 現所属）  ※現所属は同姓同名対策のため必ず記載
- 昇格・降格の場合: 氏名（現役職 → 新役職、バンド: Xxx）※バンドはスライドに明記の場合のみ

操作種別が不明または情報不足の場合は、変更セクションには入れず、
末尾の「❓ 要確認:」セクションに「氏名（理由）」の形式で列挙すること。

人物・組織・変更に関係のないテキスト（ロゴ、装飾、スライドタイトル、日付等）は無視すること。
変更のない人物は記載しないこと。

【スライドテキスト】
{ここに抽出したテキストを貼り付ける}
```

## Stage 2: アプリのAIエージェント処理フロー（計画・未実装）

> Stage 2 は現時点で未実装（`apps/web/src/infrastructure/` に PPTX 関連コードなし）。
> `chatSession.ts` の `BASE_SYSTEM_PROMPT` にフロー定義を追加すれば会話ベースで動作させられる想定だが、
> 専用の system prompt セクション・サマリー widget は未着手。以下は実装時の計画方針。

変更指示テキストをチャットに貼り付ける（「以下の体制図変更指示を処理してください」または `## 異動` 等の見出しを含むテキストをそのまま貼り付け）と、AIエージェントが3フェーズで処理する構想。

1. **Phase 1 - サマリー確認**: 変更指示テキストを解析し、変更種別ごとの件数を「確定（情報が揃っている）」と
   「要確認（バンド未確定の昇格・❓ 要確認項目など）」に分けて提示し、ユーザーが内容を確認する。
2. **Phase 2 - 要確認項目のレビュー**: 情報不足の項目を優先順位（バンド未確定 → ❓ 要確認 → 同姓同名等の人物特定）
   の順に1件ずつ確認する。`getFieldOptions` で選択肢を提示し、確定なら次へ、スキップなら `propose_field_edit` で
   `memo` に `要確認: {内容}` を記入して次へ進む。
3. **Phase 3 - 一括実行**: 確定した変更を実行する。同じ行先への異動は `propose_bulk_transfer` でまとめ、
   昇格・降格は `propose_promotion` / `propose_change_position` を使う。実行後は `getReviewSummary` で件数を確認し、
   `getValidationDiagnosis` で自動修正可能な問題を提案する。

Phase 3 で使うツール自体（`propose_bulk_transfer` 等）は既存実装で対応可能。未着手なのは Phase 1/2 の
会話フロー制御（system prompt への追記）のみ。
