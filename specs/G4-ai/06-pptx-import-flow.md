# G4-06: 体制図インポートフロー仕様

体制図PPTX/画像から人事変更指示を生成し、このアプリのAIエージェントで対話的にレビュー・実行する2段階フロー。

---

## 概要

```
[Stage 1] 外部ツール（LLM等）
  体制図PPTX/画像 → 変更指示テキスト（本ドキュメントの形式）

[Stage 2] このアプリのAIエージェント
  変更指示テキスト → サマリー確認 → 要確認項目レビュー → 一括実行
```

Stage 1 と Stage 2 のインターフェースは「変更指示テキスト」のみ。外部ツールとこのアプリは疎結合。

---

## Stage 1: 外部ツールへの要件

### 期待するアウトプット形式

```
## 異動（→ 行先部署名）
- 田中太郎（現: 営業本部）
- 鈴木花子（現: 営業本部）

## 異動（→ 経営企画部）
- 佐藤次郎（現: 総務部）

## 昇格
- 山田一郎（主任 → 課長）
- 中村健（課長 → 部長、バンド: M4）

## 降格
- 高橋誠（部長 → 課長）

## 役職変更（昇降格なし）
- 渡辺美咲（チームリーダー → スペシャリスト）

## 社内兼務追加
- 加藤拓也（本務: 開発部） ← 品質保証部

## 社内兼務解除
- 伊藤さくら（本務: 人事部）の品質保証部 兼務を解除

## 本務出向
- 松本隆（現: 経営企画部） → 株式会社○○ 営業部

## 兼務出向
- 木村智子（本務: 開発部） ← 株式会社△△ 技術部（兼務）

## 本務出向解除
- 吉田健二（株式会社○○ 出向中）→ 本務復帰

## 休職
- 小林美和

## 復職
- 森田誠

## 移籍（出る）
- 田村浩（現: 営業部） → 株式会社○○へ移籍

## 退職
- 西川一郎

❓ 要確認:
- 大野裕子（役職変更か異動か不明）
- 原田一郎（昇格と思われるがバンド不明）
```

### フォーマットルール

| ルール | 内容 |
|---|---|
| 変更種別の見出し | `##` で明示する。「→」だけでは異動か出向か判断できないため必須 |
| 異動のグループ化 | **同じ行先の人は1つの見出しにまとめる**（`propose_bulk_transfer` 最適化のため） |
| 人名 | フルネーム必須。同姓同名対策に現所属を `（現: 〇〇部）` で添える |
| 部署名 | 正式名称。略称は使わない |
| バンド | スライドに明記されている場合のみ記載。不明な場合は省略（アプリ側で確認する） |
| 要確認 | 操作種別が読み取れない・情報不足の場合は `❓ 要確認:` セクションに列挙 |
| ノイズ除去 | ロゴ・装飾・スライドタイトル・コメント等は除外する |

### 変更種別と EditPattern の対応

| 指示テキストの見出し | アプリ内 EditPattern | 備考 |
|---|---|---|
| 異動 | 社内異動（orgTransfer） | 行先部署ごとにグループ化 |
| 昇格 | 昇格（promotion） | バンド未確定の場合は Phase 2 で確認 |
| 降格 | 降格（demotion） | |
| 役職変更（昇降格なし） | 役職変更（titleChange） | バンド変化なし |
| ジョブタイプ変更 | ジョブタイプ変更（jobTypeChange） | 職種変更 |
| 雇用延長 | 雇用延長（employmentExtension） | |
| 社内兼務追加 | 社内兼務追加（concurrentAdd） | |
| 社内兼務解除 | 社内兼務解除（concurrentRelease） | |
| 本務出向 | 本務出向（secondmentOut） | |
| 本務出向受入 | 本務出向受入（secondmentIn） | 受け入れ側の操作 |
| 本務出向解除 | 本務出向解除（secondmentOutRelease） | |
| 本務出向受入解除 | 本務出向受入解除（secondmentInRelease） | |

### Stage 1 プロンプト例（外部LLMに渡すプロンプト）

体制図のスライドテキストを外部LLM（Claude/GPT-4o等）に渡す際のプロンプト。

```
あなたは人事異動情報の構造化アシスタントです。
以下のスライドテキストを読み取り、人事異動の変更指示を指定の形式で出力してください。

【出力形式】

変更種別ごとにセクションを作り、該当者を列挙してください。
使用するセクション見出し（## ）は以下のいずれかのみ使用してください:
  異動（→ 行先部署名）、昇格、降格、役職変更（昇降格なし）、ジョブタイプ変更、雇用延長、
  社内兼務追加、社内兼務解除、
  本務出向、本務出向受入、本務出向解除、本務出向受入解除、
  兼務出向、兼務出向受入、兼務出向解除、兼務出向受入解除、
  休職、復職、移籍（出る）、移籍（入る）、退職

異動は行先部署ごとにグループ化し、
見出しを「## 異動（→ 行先部署名）」とすること。

各人物の記載形式:
- 氏名（現: 現所属）  ※現所属は同姓同名対策のため必ず記載
- 昇格・降格の場合: 氏名（現役職 → 新役職、バンド: Xxx）※バンドはスライドに明記の場合のみ

操作種別が不明または情報不足の場合は、変更セクションには入れず、
末尾の「❓ 要確認:」セクションに「氏名（理由）」の形式で列挙すること。

人物・組織・変更に関係のないテキスト（ロゴ、装飾、スライドタイトル、日付等）は無視すること。
変更のない人物は記載しないこと。

【スライドテキスト】
{ここに抽出したテキストを貼り付ける}
```

## Stage 2: アプリのAIエージェント処理フロー

変更指示テキストをチャットに貼り付けると、AIエージェントが以下の3フェーズで処理する。

### トリガー

ユーザーが以下のいずれかの形でテキストを貼り付けたとき:
- 「以下の体制図変更指示を処理してください」で始まるメッセージ
- 変更指示テキストをそのまま貼り付け（`## 異動` 等の見出しを含む）

---

### Phase 1: サマリー確認

AIが変更指示テキストを解析し、変更種別ごとの件数をサマリーとして提示する。

```
AI: 以下の変更指示を受け取りました。確認してください。

  ✅ 確定（情報が揃っている）
    異動:           8名
    社内兼務追加:   2名
    本務出向:       1名
    休職:           1名

  ⚠️ 要確認（このあと1件ずつ確認します）
    昇格（バンド未確定）: 3名
    ❓ 要確認:           2件

  合計 17件の変更です。内容は合っていますか？

ユーザー: 合ってます
ユーザー: 異動は7名のはず  → AI が差異を特定して確認
```

---

### Phase 2: 要確認項目のレビュー

情報不足の項目を1件ずつ確認する。確定したら次へ、スキップしたら `memo` に記録して次へ。

**優先順位（この順で確認する）:**
1. 昇格・降格のバンド未確定
2. ❓ 要確認 として上がっている項目
3. 同姓同名など人物が特定できない場合

**バンド確認の例:**

```
AI: 山田一郎さんの昇格（主任 → 課長）について確認します。
    現在のバンドは M2 です。
    課長の典型バンドは M3 または M4 です。どちらですか？

ユーザー: M3                    → 確定
ユーザー: わからない            → スキップ（memoに「バンド要確認」を記入）
ユーザー: M3の根拠を教えて      → AI説明 → 確定 or スキップ
```

**❓ 要確認 の例:**

```
AI: 「大野裕子（役職変更か異動か不明）」について確認します。
    役職変更ですか？それとも異動ですか？

ユーザー: 異動です、○○部へ     → 確定
ユーザー: スキップして          → memoに「変更種別要確認」を記入して次へ
```

**スキップ時の memo 記入形式:**

```
要確認: バンド未確定（昇格 主任→課長）
要確認: 変更種別不明
要確認: 異動先部署名を確認してください
```

---

### Phase 3: 一括実行

確定した変更を実行する。

**実行ルール:**
- 同じ行先への異動は `propose_bulk_transfer` でまとめる（1回で実行）
- 昇格・降格は `propose_promotion` / `propose_change_position` を使う
- バンドが確定している場合は `propose_field_edit` でバンドも同時に設定
- スキップ項目は `propose_field_edit` で `memo` フィールドに「要確認: 〇〇」を記入してから実行

**実行後:**
- `getReviewSummary` でサマリーを取得して変更件数を確認
- `getValidationDiagnosis` でバリデーション問題を確認し、自動修正可能なものから提案

## システムプロンプト追加（実装ガイド）

`apps/web/src/application/chatSession.ts` の `BASE_SYSTEM_PROMPT` に以下セクションを追加することで Phase 1〜3 が動作する。

```
## 体制図インポートフロー
「以下の体制図変更指示を処理してください」や「## 異動」「## 昇格」を含む変更指示テキストを受け取ったとき、
以下の3フェーズで処理する:

Phase 1 - サマリー確認:
  変更種別ごとの件数をまとめ、確定できるものと要確認のものを分けて提示する。
  ユーザーが「合っている」と確認してから次へ進む。

Phase 2 - 要確認項目レビュー（バンド未確定の昇格 → ❓ 要確認 の順）:
  - getFieldOptions でバンド・役職の選択肢を取得してユーザーに提示する
  - 役職名から典型バンドを推測してよいが「推測です」と明示する
  - ユーザーが「わからない」「スキップ」→ propose_field_edit で memo に「要確認: {内容}」を記入して次へ
  - 全件確認が終わったら Phase 3 に進む

Phase 3 - 一括実行:
  - 同じ行先への異動は propose_bulk_transfer でまとめる
  - 全実行後に getReviewSummary で変更件数を確認してユーザーに報告する
```
